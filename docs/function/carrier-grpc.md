# The gRPC carrier

gRPC is the most expensive carrier in the matrix and it is expensive because of HTTP/2, not because of anything this tree does. What this tree controls is the envelope: a 5-byte gRPC length prefix, a compressed-flag byte, and a protobuf `Hunk` carrying one `bytes Data = 1` field. One `Hunk` is exactly one buffer that came from above, at most `16375` bytes: the most whose envelope and tag still fit a DATA frame one byte under the `16384` the peer advertises, so a message is never cut across two frames, a peer never reassembles one, and four hunks fit the `65535`-byte stream window a peer starts at where four full frames are one byte over. The payload bytes are the proxy's own, unchanged.

Write never touches the payload. The 5-byte gRPC envelope and the `Hunk` tag and varint are assembled in a small prefix buffer, and the caller's payload is handed to HTTP/2 as a separate frozen slice beside it — a frame's head and envelope prefix in a batch slot of their own, its payload still the caller's slice — so the bytes the proxy passed down are the bytes the socket carries, and no payload byte is staged into a message buffer first. Before this shape the payload was copied into a `Hunk`, then into an envelope, then once more per flow-control window; none of those copies survive here.

Those frames do not leave one at a time either. A caller write's frames are gathered and flushed as one vectored call, so a relay's full `64 KiB` read — five hunks, five DATA frames, ten segments — is one `writev` on unix and one `WSASend` on Windows, where a read of four hunks used to cost eight socket calls on unix and twenty there, a frame having been sent part by part wherever the platform had no `writev`. A batch does not hold frames behind credit it has not been given: the window is still taken per frame, and when it is not there the gathered frames go out first, because a peer grants for bytes it has seen. The relay's parked turn then waits up to `RELAY_POLL` on the carrier's `WINDOW_UPDATE`, so a peer that grants for the flush wakes the lane instead of pacing it at one window per quantum; a peer that grants nothing still costs the turn it already cost.

The relay's path never waits on a write either, though it waits a bounded turn on a window. `CarrierSink::push` takes the window for a whole message. When that window is not there it first flushes the frames it already gathered — a peer grants for bytes it has seen — and answers `Push::Took(flushed)` for the prefix it sent, or `Parked` when it sent nothing; the lane re-offers only the rest and spends the parked turn in `CarrierSink::wait_for_room`, which gRPC ends on the peer's `WINDOW_UPDATE` and every other carrier sleeps out. A message is one window's unit here because a piece split across two windows would flush its first half and be offered whole again on the retry, duplicating it. Both transports arm a one-millisecond write clock — a TLS or REALITY session through the raw descriptor it exposes, plaintext through the tail below — so a write the socket cannot finish keeps its unwritten suffix instead of parking the lane in `sendto`: a sealed record beyond `PACED_TAIL` (`256 KiB`) refuses the next offer and the lane parks, and a plaintext tail drains before adding and refuses past the same `256 KiB`, while a control frame the demux writes appends behind a parked tail because no lane may wait for it. A `settle` step drains that suffix before the lane reads again, because the credit a parked write waits for arrives on the next frame of the peer, and this lane is the one that reads it. The plaintext socket takes the caller's slices straight to `writev`; only the suffix a timed-out write left behind is copied into the tail, because the relay buffer behind it is overwritten on the next read. Before this, `push` took the window with a wait and wrote the frame blockingly while holding the carrier's stream lock, so a full send buffer parked every lane in `sendto` and the read that would have granted the credit waited behind the write that needed it; a flow died at its first frame once the client stopped uploading. `proxy::tests::eight_downloads_finish_over_each_grpc_carrier` runs eight downloads over each of the plaintext, TLS and REALITY carriers. What this does not remove: one `setsockopt` per direction, the record copies inside the TLS session, and the last bytes of a parked tail still leave from a copy; a session that exposes no raw descriptor (ECH, KCP) keeps the blocking write, so a peer there can still park a lane.

Read has one buffer. A DATA frame's body is read onto the end of the message buffer, the envelope and the `Hunk` are parsed where they landed — one message per frame from this tree, and the reader still takes a message a peer splits — and the payload is delivered out of that buffer at the offset the parser found. A relay takes it as a window over that same buffer and writes that run to the peer socket, so a relayed byte is copied once on the way through, into user space by the socket read; only a caller that asks through `Read` — a handshake, or the sealed-VLESS reply reader — still copies into its own buffer. What a body owes the peer accumulates instead of leaving: one credit pays for the bodies that landed since the last one, as the two `WINDOW_UPDATE` frames — eighteen constant header bytes differing only by stream id and the increment — in one write, and it is owed once half the advertised window has arrived. That grant only holds because the preface pays the peer the whole connection window at once, since a batched credit cannot be the thing that raises it. The cursor skips the protobuf fields this lane does not read without moving them, and the dead prefix is reclaimed before the next body is appended, which is what keeps one buffer enough. There is no second buffer to stage into and no backlog to join one to.

One listener serves both methods the service defines. `rpc Tun` streams a `Hunk` — one `bytes Data = 1` — and `rpc TunMulti` streams a `MultiHunk`, whose field 1 is `repeated bytes`, so one message carries the batch a writer's `WriteMultiBuffer` holds: Xray's server reads the echo through a `readv` reader that doubles up to eight 8 KiB buffers and puts one element per buffer into a single message (`transport/internet/grpc/encoding/multiconn.go:115-134`). A served call's method is the `:path` it used — the configured path, or the same path with `TunMulti` for the last segment — because the two shapes cannot share a decoder: a `MultiHunk` read as a `Hunk` hands the caller only the last element of every message, which is a silent truncation rather than an error. The mode is the caller's choice, not the listener's, the way Xray's hub registers both handlers from one config (`transport/internet/grpc/hub.go:124`). In multi mode the cursor stops being per-message and becomes per-element: an element's own bytes end exactly where the next element's key begins, so a batch is delivered from the one message buffer in order, element by element, with no staging move — `8` on the batched row is eight 8 KiB elements arriving from two messages, and its `0` is the same `staged` counter the single-mode rows use. The writer now gathers consecutive elements into a `MultiHunk` message, and the relay asks the writer for the most it can frame (`CarrierSink::read_window`), so at the default `65_535`-byte window a `65_471`-byte read is one message with four elements; the fourth is the remainder, `multi-messages-per-relay-read 1` against `single-messages-per-relay-read 5`; an offer larger than the credit the peer has left still splits at it, because a peer cannot grant for bytes it has not seen. The window for the whole message is taken before its first frame and the message is added only to a batch that can hold every frame, so a message is never half-sent and retried. Its element is the largest whose complete envelope — prefix, tag and length — fits the live room, so a message that fits is not cut for a fixed margin; a blocking write with no room waits for the credit instead of freezing a one-byte element for the rest of the write. The dial side now follows the reference's derivation (`transport/internet/grpc/config.go:16`, `:36`, `:48`): an old-school service is escaped whole and its streams are `Tun` and `TunMulti`; an empty service keeps its empty segment (`//Tun`, `//TunMulti`); and a custom path names the service in every segment before the last and the streams in the last one, split on `|` when both are named. `grpcSettings.multiMode` selects the multi stream on the dial, and the client decoder is opened as `MultiHunk` from the config (`transport/internet/grpc/dial.go:60-69`), so a batch is delivered element by element instead of the last element of every message. The head carries `authority`, `userAgent` mapped the way the reference maps `chrome`, `firefox`, `edge` and `golang`, and the preface advertises `initialWindowsSize`; `idleTimeout` and `healthCheckTimeout` arm one keepalive thread that sends `PING` and requires its `ACK`. `permitWithoutStream` is read but not enforced: the listener does not apply the keepalive-PING policy when no stream is active. The listener owns one HTTP/2 connection for many calls: the preface is read once, `SETTINGS` and the connection window are answered once, and every subsequent `HEADERS` block is gated and handed to `H2Service::open`, which opens that stream's reader and writer on the shared demux instead of the socket. The demux caps the table at `MAX_STREAMS` (100), frees a stream's id once both halves end, and advertises no `MAX_CONCURRENT_STREAMS`, so a client may open the next stream before the last ends, the way the reference's HTTP/2 server does; `ferrox-app-grpc::tests::one_connection_serves_two_streams_at_once` drives two calls over one loopback preface. Each stream's `WINDOW_UPDATE` and `DATA` are framed by the connection, so a message still leaves as one DATA frame and a short window splits it rather than joining it to the next message. The connection's handshake clock stops when the first stream's opening request is decoded, so a peer that sends the preface and then nothing still releases the accept thread instead of parking it. What is still not here: no `grpc-status` trailer is written after a call ends, which a grpc-go client would require but the raw HTTP/2 clients this carrier serves do not read; the authority falls back to the dial host rather than `tlsSettings.serverName`; and a custom service without `|` names one stream for both methods, so the listener treats it as single mode rather than registering two handlers under one name.

## The poll it hands back

A gRPC frame is parsed in place and resumed: `pending`, `frame_head` and `frame_have` hold a half-read length prefix or message across a poll timeout, `pump` saves the bytes it filled back into `pending` before it propagates an error, and `begin_data`/`finish_data` keep the DATA frame's buffer. A lane's expired quantum returns to the lane; a spent handshake clock ends the read hard, so `read_exact` stops retrying. Syscalls per frame are unchanged. Witnessed by the silent-peer set, `proxy::tests::a_silent_peer_cannot_pin_a_grpc_request_head` and its siblings across the four protocols.

The connection's own demux resumes the same way. `xhttp_h2::Frames` keeps the preface, the frame head and the body across a poll timeout, so one call settles on the next frame, on a quiet socket, or on the end; the blocking accept path keeps retrying a timeout exactly as the reader did, and the plaintext gRPC path hands the lane back with `Next::Idle` once the socket answers nothing, where the read has already named the descriptor. The relay pool parks that lane on the socket's readiness, so a connection costs a readiness slot until its peer speaks, not a thread for its lifetime: `proxy::tests::muxed_grpc_connections_share_the_lane_pool` holds eight muxed connections over the pools it warmed and fails if the process grows by a demux thread per connection. A sealed session exposes no socket for the pool to poll, so its lane parks on the timer path; `serve_muxed` no longer spawns a thread for it, and `grpc::tests::a_sealed_demux_rides_the_lane_pool` holds sixteen silent sealed connections at the pool's lane count.

`payload-staging-copies-per-byte-read` is the reader's own `staged` counter, the shape `xtls-vision` uses: it counts the bytes this lane moves for itself, which are the only copies a byte test cannot see. It is driven from an in-memory server that answers whole frames, over the three shapes a body can arrive in — one message per frame, two messages in one frame, one message split over frames. The `0` on the padded row is that gate's own message opened behind a pad byte: the parser steps over the byte and the frame's length drops the tail, so nothing moves; a second padded test cuts a pad byte into a message the frame before had started and shows the counter at `5`, the move that shape still pays. `reclaim-moves-per-drained-buffer` counts the reclaim *calls* that copy live bytes — the operation `staged` cannot see, because a fully drained buffer leaves an empty run that is zero bytes moved either way. A caller that takes each whole `HUNK` before the next arrives leaves nothing live, so the reclaim is a `clear` and the counter holds at `0` over three `HUNK` frames in `the_message_buffer_is_reused_not_reallocated`, the same test that gates the buffer's capacity as steady. The three credit rows come from one test over an in-memory peer that keeps each write it was given: full `HUNK` bodies are delivered and counted, and the test fails if a credit leaves before `credit-bytes` of bodies have landed, if the grant is more than one write, or if that write is not the peer's two frames with the increment of every body since the last grant — `128` frames of `16_384` bytes per credit, on a downlink of whole messages, where the lane used to write one pair per frame. The preface row is read off the first write both halves of a call make: the setting and the `WINDOW_UPDATE` on stream `0` that lifts the connection to the window the setting advertises, which is the grant a batched credit rests on. The eight `pinned-threads` rows are one serve thread each, watched through a channel: a peer that opens and never speaks, one that sends the `24`-octet preface and stops, and six that dial a real gRPC client, answer the head, and never send the opening request — for `vless`, for `trojan`, `vmess`, `shadowsocks` and `shadowsocks-2022` each decoding its own head, and one through a TLS session, where `accept_split` answers the head and only the request's own clock is left to end the flow. The `0` is a give-up at `budgets::handshake()` rather than a race, and each row was audited by taking its own arm away first — the preface read's deadline, the pump's, the reader's, then the session caller's — and reading the test fail at its `15s` bound. The five plaintext rows share one arm, `proxy::under_handshake`, so the control that audits them removes it once and the five fail together; `accept` hands the caller a reader whose poll and clock it has already cleared, and a protocol that then reads its own request through it would wait unbounded. The session row needs no socket arm: the dispatchers behind it already poll the session's socket at `RELAY_POLL`, so the read answers on a grain and it is the deadline that turns the silence into a refusal. The batched row counts the elements one `TunMulti` message hands over before the caller sees a gap: eight 8 KiB elements in two messages, each element delivered from where it lay, so the row's `0` is the same `staged` counter and the eight 8 KiB runs are the assertion that no element was dropped or reordered — the failure `hunk_decode` would give is the last element of each message and nothing else. The methods row is served from a scripted wire: `Tun` with a `Hunk`, `TunMulti` with a batch, and a third path that is neither and is refused. The four header rows are the decoder handing a block's fields over borrowed rather than built: `header-field-copies-per-head` records the address every field arrives at and fails unless it lies inside the block the caller passed, at the offset where that field's own bytes are. `table-entry-copies-per-indexed-field` requires the pair a dynamic entry is and the pair the consumer was handed to be the same two addresses — once for the insert that made the entry, once for the index that names it afterwards. `decoder-buffer-writes-per-borrowed-field` warms the decoder's Huffman buffers, then reads a block of one index and one plain literal, and fails if either buffer's pointer or capacity moves or either ends the block holding bytes. The inserted row is the `2` those two allocations still cost: a name and a value the table keeps after the block is gone. The five write rows are two tests over the same in-memory peer, given a full relay read of `64 KiB`: the single-mode test counts the writes the batch cost (`1`), the segments the one write carries (`10`, a head slot and a payload run for each of the five frames), how many of those runs are the caller's own buffer (`5`, edge to edge, no gap and no byte twice) and the messages the read leaves as (`single-messages-per-relay-read 5`), and it compares the whole batch against a frame-by-frame reference built at the same `max_frame`, so a gather that reordered or restaged a frame fails as different bytes rather than as a count; the multi-mode test sends the writer's own read window as one `MultiHunk` message (`multi-messages-per-relay-read 1`), builds its elements from the caller's buffer, and checks every payload run edge to edge; the writer's split at an offer larger than its starting window is the second test, which keeps its two-message shape without carrying a row. `a_wide_batch_reaches_a_real_socket_whole` puts the same ten segments through a real socket, which is where a platform that split the list or refused its width would show it — as missing bytes, the only thing a loopback test can assert. Neither is a count the socket can gate: `writes-per-relay-read` is driven from the in-memory peer, exactly as `window-update-writes-per-credit` is. `the_tail_hands_the_payload_to_the_socket_by_pointer` is the plaintext path of the same claim: the base the recorder sees is the caller's buffer, so the tail in front of a bare socket is not a staging copy, and `the_tail_keeps_what_a_timed_out_socket_did_not_take` is the one shape where it does copy — a write that ends before the bytes do — holding the order through `settle`. `a_gathered_batch_flushes_before_a_window_that_has_not_arrived` is the deadlock witness the batch needs and does not carry a row: a peer grants for bytes it has seen, so frames held in a batch cannot wait behind the window only those frames would raise, and the test watches a real write appear while the writer thread is still parked inside the same `send`, then joins it once the credit arrives. None of those numbers is a duration, and `## Time` says why.

## What we removed

- **A gRPC settings object that was parsed and dropped.** `authority`, `userAgent`, `multiMode`, `idleTimeout`, `healthCheckTimeout`, `permitWithoutStream`, `initialWindowsSize` and the `|` split of `serviceName` were all read by the reference and ignored here. The service string now derives both stream names, `multiMode` asks for the multi stream and opens the client decoder in the matching shape, the request head carries the configured authority and user agent, the preface advertises the configured stream window, and the keepalive fields arm a `PING`/`ACK` thread. `grpc::tests::grpc_settings_reach_the_preface_and_head` reads the preface and decoded head, `grpc::tests::a_multi_mode_dial_reads_the_batch_it_asked_for` reads a `MultiHunk` through the config-selected decoder, and `proxy::tests::a_grpc_service_name_is_escaped_the_way_xray_escapes_it` holds the custom-path split. What did not move: the bytes of a single-mode call and the fallback authority — the last still names the dial host where the reference would use `tlsSettings.serverName`.
- **The per-element message on the multi-mode writer.** A `TunMulti` writer sent one `Hunk` per element, so the reference's `WriteMultiBuffer` batch was gathered only on the receive side. Consecutive elements now go into a `MultiHunk` message, and the relay reads at most the window the writer can frame in one message (`CarrierSink::read_window`): at the default `65_535`-byte window a `65_471`-byte read is one message with four elements; the fourth is the remainder, `multi-messages-per-relay-read 1` against `single-messages-per-relay-read 5`, where a full `64 KiB` read used to leave a 36-byte second message that emptied the window and parked the lane. The message is added only to a batch that can hold every frame, with the window for the whole message taken before its first frame, so a message is never half-sent and retried; a group is capped at the credit the peer has left, because a peer cannot grant for bytes it has not seen. `a_multi_relay_read_at_the_peer_window_is_one_message` builds that message's elements from the caller's buffer, checks every payload run edge to edge and holds the buffer's pointer and capacity; `a_multi_read_fits_a_small_window_and_follows_credit` reads `9_984` bytes on a `10_000`-byte window as one message and then at `1_976` after the first write leaves that much credit; `a_multi_relay_read_batches_the_window_it_can_pay_for` keeps the split at an offer larger than the starting window. On a promoted buffer the `65_471` limit makes a full `64 KiB` source two relay reads, `65_471` then `65`, where the unlimited window read it in one, so `relay-reads-per-promoted-64KiB-window 2` and `source-read-syscalls-per-promoted-64KiB-window 2` record the granularity change; live credit can turn the tail into further short reads before the peer's update arrives. What it does not remove: the DATA frames the message is split into, the payload bytes, which are unchanged, the extra source read, and up to `64` bytes of each relay read, the envelope and tags the cap holds back; a small window is read at its own size instead of the relay's `16 KiB` default. The server-thread ratios for the same cell are still filed under #696: the branch reads `15/15/17/16/16` ferrox server threads against `11/13/13/14/13` xray-core across plaintext, plaintext-multi, REALITY, TLS and TLS-multi (`1.36`, `1.15`, `1.31`, `1.14`, `1.23`), inside the `1.54`–`1.67` filed in `scripts/leg-gaps.txt`; that is the muxed demux's lane, not the writer's read cap.
- **A credit that forgot the padding.** RFC 7540 6.9 puts the whole DATA payload into the flow-control window, the Pad Length octet and the Padding included, but the credit was what the cut left, so a padded frame gave the peer back `1 + pad` octets fewer than it had sent. A peer that keeps a strict window loses that much a frame, and a long flow loses its window and stalls. The credit is the wire length now, and `a_padded_frame_credits_its_whole_wire_payload` is the witness: it reads the `WINDOW_UPDATE` increments off a padded frame and holds them at the frames' wire length, where the cut's length is what the credit used to carry. What did not move: the bytes on the wire, and the padding's own cut — the payload still arrives trimmed, and the credit is what the frame cost the peer, not what the payload was worth.
- **A grown header block.** The HPACK literal block was written into a buffer that started empty, so a head with a few fields reallocated it a few times before it held them. The block's own length is known before it is written — the never-indexed prefix, the two length prefixes and the two runs of bytes — so the buffer is opened once at that length. The counting allocator is the witness: `a_header_block_is_opened_once` holds the block at one allocation and at its own length, where the grown shape paid four. The bytes on the wire do not move: the same literals are written in the same order, and the xHTTP lane's head rides the same coder.
- **The envelope chain.** Xray's `transport/internet/grpc/encoding/hunkconn.go` copies the hunk into the caller's buffer on every `Read` (`:68-82`), adopts the protobuf's slice only when `cap(h.buf) >= buf.Size` (`:97`) and copies otherwise, and allocates a `&Hunk{...}` per write (`:108-118`). The HTTP/2 side then does its own copy into a 32 KiB `bufWriter` (`grpc@v1.84.0/internal/transport/http_util.go:328-353`), and the read side allocates a fresh buffer per DATA frame (`:545-556`). sing-box's `transport/v2raygrpc/conn.go:37-52` does `copy(b, hunk.Data)` into the caller's buffer and stashes the tail in a cache, through grpc-go, so a `Hunk{Data: b}` is a protobuf marshal per write.
- **The loop in the common varint and envelope.** `read_varint` walked a `(0..70).step_by(7)` loop for every key and length, and `frame_prefix` looped over the payload length's varint even when it was one byte. A one-byte varint now returns from a single check, and a sub-`0x4000` envelope length writes its two bytes directly; the general varint keeps the loop. The probe reads `73251` against `86563` on the same base, `13312` (`15.4%`) fewer, and `frame_prefix_matches_the_vec_form_at_varint_edges` still holds the bytes at `0`, `127`, `128`, `16383`, `16384`, `1 << 21` and `1 << 28`; the messages, offsets and prefixes are unchanged. What this does not remove: the general varint's loop, and the payload bytes themselves.
- **The writer's varint length.** `varint_len`, the seven-bit group count the batch capacity and `message_payload` use, walked a shift loop; it is now `(64 - value.leading_zeros() as usize).div_ceil(7).max(1)`, and `varint_len_matches_the_written_length_at_every_boundary` holds it equal to `write_varint` at both edges of every width. `read_varint` and `frame_prefix`'s above-`0x4000` path still loop.
- **The quadratic drain.** Consuming a pending buffer with `Vec::drain` moves every remaining byte for every message, so a burst of N messages in one window costs O(N²) bytes moved. One cursor consumes the message buffer, and the reclaim that keeps it bounded moves only what is still live, once per appended body.
- **The reader's own staging hop.** Until this page's read rows were written the way they read now, the path was socket → frame scratch → message buffer → backlog → caller: the DATA body was `extend`ed into `msg`, `hunk_decode` borrowed it, and the very next statement copied that borrow into a backlog because the caller had not asked for it yet. Two of those three moves are now gone — the body is read straight onto the end of `msg` and the payload is delivered where it lies — which is what `payload-staging-copies-per-byte-read 0` counts. `user-space-copies-per-byte-read 1` was the row before, and no test observed it: `tunnel_carries_an_echo_over_loopback` is a byte test, and a byte test cannot see a copy. It is replaced by the counter, not re-blessed.
- **A second allocation per message.** The message buffer is reused across writes, and the HTTP/2 layer takes it by `split().freeze()` so the refcount, not a copy, is what crosses the boundary. On the read side the same buffer now serves every frame, gated by `message-buffer-reallocations-per-same-sized-frame 0`.
- **The write-side copy that was never there.** `user-space-copies-per-byte-written` read `1` and named `hunks_carry_the_xray_schema_bytes`, a byte test that cannot see a copy — the bytes are identical whether the payload is staged or handed straight to the socket. The carrier already assembles the frame header, the envelope prefix and the caller's payload as three separate slices and passes them to a `writev`, so the true count at this layer is `0`. The row is not re-blessed to a nicer number: it is given the witness it never had — `the_uplink_hands_the_payload_to_the_writer_by_pointer` records the base of every slice that reaches the frame writer and fails unless one of them *is* the caller's buffer, at the payload's full length.
- **The second write per credit.** A credit is two `WINDOW_UPDATE` frames, one for the connection and one for the stream, and each was built and written on its own. Their eighteen header bytes are constant and only the stream id and the increment differ, so both come out of one 26-byte template in a single write — the same two frames, in the same order, one write syscall fewer per DATA frame. What this leaves alone: `xhttp_h2`'s `replenish` credits the same pair as two frames over two writes, and its page owns that row.
- **The frame a message did not fit.** A hunk of `16_384` payload makes a `16_392`-byte body, eight over the `16_384` a DATA frame carries, so every hunk left as a full frame and an eight-byte frame of its own. A peer that parses a message where it lands reassembled one from two frames for every hunk — `65_536` times a GiB. The writer now sizes each Hunk by the frame it will occupy, one byte under the advertised width: `16_375` payload, one message per frame, five frames per `64 KiB` read instead of eight, and the same payload bytes in the same order. The byte under the frame is the window's: four `16_384`-byte frames are one byte over the `65_535` a peer starts at and the fourth waits for a credit, where four `16_383`-byte frames fit it. `a_hunk_fits_the_frame_that_carries_it` is the witness: it walks every DATA frame the writer emitted, fails unless the gRPC length the frame announces is exactly its body, and compares the reassembled payload to the caller's buffer; the old shape fails on its first frame. The reference's server sends `8 KiB` hunks, one frame each, so this removes a cost the comparator never paid. What it costs: the fifth frame of a read is the remainder, and a write shorter than the payload still leaves a whole frame for its own message.
- **The credit per frame.** A downlink is `81_920` messages per GiB — four full frames and a remainder in every `64 KiB` read — and every one of them was credited and locked as it landed: `81_920` writes of `26` bytes and `81_920` takes of the frame-write mutex, beside the `163_840` writes that carry the payload — one DATA frame per hunk at the `16_383` this lane now packs. Bodies now add to a counter and one credit pays the counter when it reaches half the advertised window, so a GiB costs `512` credit writes and `512` locks — `128` messages per credit by the arithmetic on the page's own `hunk-payload-bytes` and `credit-bytes` rows, witnessed message by message by `a_credit_grants_the_window_it_owes_in_one_write`. The two windows can only be batched because the preface pays the peer the connection window that setting implies: one `13`-byte `WINDOW_UPDATE` on stream `0` per connection, added where the settings already went, in the same write. What is not flushed: a credit that has not reached `credit-bytes` when the stream ends is never sent, because the peer still holds at least the other half of the window and can fill it without waiting — the bound the same test reads off its own measured increment.
- **The socket call per frame.** The same `81_920` frames per GiB each took the frame-write mutex and made a call of their own: `2` per hunk on unix, where a frame went out as head and body in one `writev`, and `10` per `64 KiB` read on Windows, where there is no `writev` and a frame's head and payload went out as one `send` each. Both cost one call per relay read, so a GiB down this lane pays `16_384` calls and `16_384` mutex takes against `131_072` of each at the hunk width on unix — the batching row's history — and every call carries ten segments rather than two or five. That is the shape of the loss the `## Time` cell prices: `95%` of this carrier's Windows cpu is kernel time, against `93%` on ubuntu at six times less of it per call, so the platform's per-call cost is exactly what the call count buys back here. What it costs: `8` slots of `25` bytes live on the stack for a caller write — `200` B written once per write, `0.3%` of the bytes that write carries — and a frame that is not the last of its batch reaches the socket when the batch fills, when the credit is short, or when the write ends, which is what the flush-before-park witness above gates. What is not removed: the frames. One DATA frame per hunk is what the envelope now fits; the fifth frame of a `64 KiB` read carries the remainder, because the payload does not divide by the frame. Collapsing that tail would take a writer that holds it for the next read, not a larger `MAX_FRAME_SIZE`.
- **The lane parked in a write only its sibling could drain.** `push` took the flow-control window with a wait and then wrote the frames blockingly, all of it while holding the carrier's stream lock. With two lanes per flow over one relay pool, a full send buffer put every worker in `sendto`, so the read that grants the credit the writer was waiting for could not run: the download stopped at the first frame after the client's upload ended, which is how the P0 regression and the `0.78×` server cell both presented. The relay path now takes the window per whole message, flushes the frames it already gathered, and waits one bounded `RELAY_POLL` turn for the `WINDOW_UPDATE` that flush earns; when the turn expires it returns `Push::Took(flushed)` with the prefix that left so the lane re-offers only the rest, and only a push that flushed nothing answers `Parked`, without waiting. Both transports keep a write clock and a bounded tail (`PACED_TAIL`, `256 KiB`, or one refused plaintext offer) that `settle` drains before the next read; the plaintext tail hands the caller's slices to the socket, so the fast path still copies nothing. What this costs: one `setsockopt(SO_SNDTIMEO)` per direction and a suffix copy only when a write times out. What is not removed: the record copies inside the TLS session, a session with no raw descriptor (ECH, KCP) still writes blocking, and a peer that grants nothing still costs a parked lane one `RELAY_POLL` turn per retry. The wait is woken by the reader's `WINDOW_UPDATE` now, so a peer that grants for the flush pays no quantum: `grpc::tests::a_parked_try_send_waits_one_quantum` reads the bounded wait and `grpc::tests::a_window_update_wakes_a_parked_take` reads the wake. The witness for the stall is `proxy::tests::eight_downloads_finish_over_each_grpc_carrier`, eight 4 MiB downloads over the plaintext, TLS and REALITY carriers, which used to time out on every one.
- **The pair per header field.** `Decoder::decode` used to answer with a `Vec<(Vec<u8>, Vec<u8>)>`: a name and a value allocated for every field of every block, which the consumer then read from and dropped. gRPC's `headers()` built one to look up four fields — `:status`, `:path`, `:method`, `content-type` — and xHTTP/H2's `open_stream` built one to take `:method` and `:path` out of it and re-emit the rest as head lines. The block now walks itself and hands each field to the visitor as it is read: an index gives up the table's own entry, a plain literal gives up the block's own run, so a field that is only read costs neither an allocation nor a copy. gRPC keeps four `Option<bool>` judged as the fields pass, and xHTTP/H2 keeps the one head buffer it was going to write anyway — sized for the bytes it carries, and its page owns that row. What is not removed: the two allocations an inserted field costs, because the dynamic table outlives the block, and one copy into the decoder's warm buffer for a Huffman-coded string, which is what the `## Measured` capacity gate is written against.
- **The setup lane a connection's demux held.** `serve_muxed` ran the H2 demux inline on whatever thread called it, and for an inbound vless-GRPC connection that thread is a setup lane — two of them, plus two borrowed. The demux owns a connection until its peer ends it, so four connections were served at a time and every other flow's front queued behind them: a client that dials one connection per flow saw one-second TTFB waves and `61` MiB/s where the same code now reads `1414`. The demux left the setup lane first, which handed it a thread of its own for the connection's life; that thread is gone too. The plaintext demux now runs as a relay lane and parks on the socket's readiness between frames, so an eight-connection cell holds the pool's lanes rather than eight more threads — `threads-per-muxed-connection 0` is `proxy::tests::muxed_grpc_connections_share_the_lane_pool`, and the matrix cell in `## Time` is the OS-thread witness the loopback test cannot be. What is not removed: the pool's reaper thread when a socket lane parks, and the lane workers themselves; a sealed session exposes no descriptor, so its lane takes the timer path instead of the reaper's set.
- **The head no peer could be refused by.** This was the only vless carrier whose opening read carried neither a poll quantum nor a wall clock: a peer that connects and says nothing, or sends the `24` octets of preface and stops, or completes the handshake and never sends its first hunk, held a relay-pool thread forever — and behind a TLS session the same stall wore a fourth shape, because `accept_split` answers the head and clears its own clock before handing the reader over, so `serve_session_grpc`'s request decode ran polled at the relay's grain with no clock, which is the pair that retries forever. Arming a quantum alone would have made it worse — `proxy::read_exact` retries a timeout by design, so a `20ms` grain with no deadline is `50` wakes a second forever — which is why the clock lives inside the reader as it does for `ws`: each of the four phases now reads under `budgets::handshake()` and is cleared again where its head ends, so the relay behind it waits blocking exactly as it did. What it costs: `4` `setsockopt` calls per accepted vless-over-gRPC flow, arm and clear at the preface and at the request head, and up to `500` wakes for a peer that never speaks. The session arm costs no `setsockopt` at all: `serve_vless_tls` and `serve_vless_reality` poll the socket under the session at `RELAY_POLL` before the handshake, so the reader only needs the clock to turn a grain into a refusal. What is armed by one function now: `proxy::under_handshake` holds the poll and the clock across one decode and puts both away on the way out, and the five plaintext reads of this carrier — `vless` and the four protocols that decode their own head behind `accept` — run through it, so the arm a caller cannot forget is the arm that does not leak. What is not unified: the http carriers' request head still runs on `budgets::head_arrival()`, because that budget names an HTTP request arriving, while this one is the carrier's opening read — the budget `serve_vless_raw` already bounds its own opening read with. What is not armed here: the `ws`, `xhttp`, `httpupgrade` and `http-header` carriers each hand their caller a reader they have already disarmed, so the same four protocols wait unbounded behind those four — `P13`'s deep-retry add-on holds the list.

What is **not** removed: HTTP/2's own framing. `T_DATA`, `T_HEADERS` and `T_SETTINGS`, HPACK and the flow-control window are the cost of the carrier, and they are the same cost Xray and sing-box pay. The 32 KiB HTTP/2 write buffer and the 4 MiB session window are named here rather than claimed as ours. Nor is the copy into the caller's buffer: a `Read` has to fill the caller's `&mut [u8]`, and that is the `1` the `## Data path` graph ends on. Two moves still survive the staging removal, and both are counted rather than hidden. A caller that leaves a payload in the buffer while the next frame arrives pays one reclaim move of what it has not taken. A pad byte that cuts into a message the frame before had started still moves what follows it down, because those bytes have to become contiguous for the parser; a pad byte that opens a message region costs a cursor step instead, which is the `0` on the padded row. `staged` counts both, which is the only reason the zeros mean anything. One accounting gap is named rather than fixed: a credit is the DATA body less its pad byte and pad tail where RFC 7540 §6.9.1 counts the whole body, so a padded frame leaves that many bytes of window unreturned — conservative, and never taken back.
