# The WebSocket carrier

`ferrox-app`'s WebSocket carrier is where the syscall shape was worst. A frame header is 2 bytes, then 0, 2 or 8 bytes of length, then a 4-byte mask, then the payload — and this tree used to spend one `read` syscall on each of those three groups plus one on the payload. Three syscalls per message, for a header that is at most 14 bytes.

Now there is one buffer. A `read` fills as much of it as the socket offers — up to 32 KiB — a frame header is parsed out of it without touching the socket, and the payload is unmasked where it lies. So a read covers a window, not a frame header: 64 frames of 21 472 bytes come out of one `read`, where the old path spent three per message before it delivered the first payload byte. A relay window fills the same way: consecutive frames already in hand are handed over together, and the lane pulls once more inside its own poll before it returns, so a server writing 8 KiB frames costs one handoff and one `writev` per 64 KiB rather than one per frame (`ws::tests::small_frames_fill_one_window`: three frames, one window, one sockcall per frame). The relay no longer copies that payload into a buffer of its own: `relay_sink_ws` takes `WindowRead::read_window`, whose spans point into `have`, and `write_all_runs` hands them to a vectored write per batch — one `writev` on unix where the socket takes the whole list, with a short write retried over the remainder and a masked `Connection` writing one span at a time. Each handed-over window stops at 64 KiB, the old relay buffer's bound, and a larger frame keeps its remainder in `have` for the next call; the bound is on the handoff, not on how much frame the reader parses. The `Read` path still copies once, for sealed carried sessions and readers that are not a `WsReader`.

The write side has two shapes. An unmasked frame goes out with `writev`, one syscall and zero copies. A masked frame stages into a thread-local buffer, and that staging is now fused: the payload is read once and its masked bytes written once, by the same `ymm`/`xor_block` ladder that unmasks in place, so the frame touches memory twice where the old `extend_from_slice`-then-`apply_mask` touched it four — a memcpy's read and write, then the mask's own read-modify-write. The mask still has to be applied somewhere and the caller still hands over a borrowed `&[u8]`, so the single copy that lands the payload in the frame is the floor; what is removed is the *second* pass over it. `apply_mask` stays a rung ladder — one 32-byte `ymm` pass per iteration on a host that reports `avx2`, the 16-byte `xor_block` ladder below it, and the byte tail under both — and `mask_copy` walks the caller's bytes through those same rungs straight into the frame, so both directions share one vector path.

## Request headers

A dial now writes the configured `wsSettings.headers` and, where the config names none of them, the reference's masked Chrome set: `User-Agent`, `Accept`, `Accept-Language`, `Cache-Control`, `DNT`, `Pragma`, `Sec-CH-UA*` and `Sec-Fetch-*` for the `ws` variant. `crate::headers::masked` owns the merge: a configured name replaces its default, a `User-Agent` naming `chrome`, `firefox`, `safari`, `edge`, `curl` or `golang` selects a mask rather than sending the literal, and the handshake's own names (`Host`, `Connection`, `Upgrade`, `Sec-WebSocket-Key`, `Sec-WebSocket-Version`) stay the builder's. `outbound_carrier` takes `Host` from the header map before `wsSettings.host`, the TLS server name and the dialled address, in that order, and `ws::tests::a_configured_header_reaches_the_handshake` holds a configured `X-Custom` and the default UA on the wire. `heartbeatPeriod` starts a timer on the shared writer that writes an `OP_PING` every period seconds and stops when the session closes or the control write fails; `ws::tests::a_configured_heartbeat_writes_a_ping_on_an_idle_session` reads that frame after one second of silence. The bytes are the reference's names and values, not a second spelling.

## Kept head

The handshake read used to `peek` for `\r\n\r\n`, prove the head there, then re-read exactly those octets so the frame behind the delimiter stayed in the socket: a head of `H` octets crossed user space twice, and every round of a head that dribbled in cost two read-family calls. `proxy::read_http_head_kept` reads once into the buffer it hands back and returns the offset where the head ends, so the head crosses once and a round costs one call — and the frame that rode in with the head is already the reader's own `have`, `at` that offset, because `split_halves` now takes the cursor instead of being handed an empty buffer. `ws::tests::a_frame_that_rode_in_with_the_head_costs_no_syscall` drives that shape from an in-memory buffer: two frames delivered with `reads()` still `0`, the buffer's base and capacity unchanged; a wrong cursor fails the bytes, a re-read fails the counter. The halves that cannot peek took the same shape with it: `proxy::read_exact_head` *is* that loop now, so `accept_split` and `connect_split` hand `split_halves` the buffer the read filled with `at` past the head instead of a `split_off`'d tail, which was a second allocation that copied the riding bytes out of the buffer they arrived in (`head-tail-allocations 0`). `ws::tests::the_record_head_hands_over_the_buffer_it_filled` watches the handover: `have` is as long as the head plus the frame, and the frame's base is the buffer's base plus the cursor — a tail of its own moves it.

What is *not* removed: `proxy::read_http_head` still answers the `http` front, whose prefix has one buffer and nowhere else to go, and the Shadowsocks rung, which waits inside a `peek` for the first byte of a request packet and must not take it.

## The poll it hands back

A relay lane owns the socket's poll quantum, so a read that comes back empty-handed is the lane's turn to move another flow, not an invitation to wait again. The VMess opening request runs under the same arm: `under_handshake` gives the frame reader the socket's poll and its own wall clock, so a peer that completes the `101` and sends no request ends at the handshake budget instead of pinning the carrier thread, and a well-formed request still decodes byte-for-byte. `WsReader` keeps a half-parsed frame at the cursor and returns the timeout: `frame` does not move the cursor until the whole frame is in `have`, so the next step resumes on the same frame. `assembling` only records that a fragmented message is open: `message` hands each complete fragment's payload over as it lands, and `compact` drops the delivered prefix even while the message is open, so a peer that never sends FIN costs one frame rather than the sum of its fragments. A handshake still in flight waits to its own deadline, and a spent clock is a hard end rather than a timeout `read_exact` would retry forever. The socket-read count per frame is unchanged; what moves is the number of `read_window` returns — one per window instead of one per message — and, with it, the lane steps and the relay writes behind them. A peer that sends only empty data frames cannot hold the lane inside a window either: sixteen of them add no span and no room, so the window returns empty-handed and the lane gets its turn, with the frames' bytes (there are none) and the bytes behind them still in order (`ws::tests::a_run_of_empty_frames_hands_the_lane_back`). Witnessed by `proxy::tests::production_tls_first_ws_matches_the_seam`, and the frame-atomic parse is the one `ws::tests::frames_round_trip_masked_and_plain` drives. A control frame buffered behind ready data is left for the next call, so a reply cannot hold a completed message behind the shared write lock, and that next call unmasks the control payload before echoing it once — `ws::tests::ready_data_leaves_before_a_buffered_ping_reply` drives the ping and the resumed fragments.

## Time

**The carrier.** The carrier is timed end to end rather than in isolation: `.github/workflows/parity.yml` runs `scripts/run-parity.sh` for `upload`, `download` and `full-duplex` across the pinned engines, and `.github/workflows/benchmark-matrix.yml` runs `vless-ws-down-8` in the standard tier on both runners. Both are CI-only because every developer machine is behind a VPN. The Windows cell is the one that priced this change: on the xray-core server, `ferrox` read **417.5 MiB/s** (0.57x of `zeronet`) with a socket-readability probe before each parked read, **755.8** (0.80x) with a single retake, **958.7** (0.92x) with the filled window, and **771.1 MiB/s (0.94x of `zeronet`) in the settled run** (`benchmark-matrix` runs `43316811127`, `43316197783`, `43316212722`, `43324983295`); the 8 KiB server frames and the lane step per frame were the deficit, and the window's one handoff per 64 KiB is what closed it. The wide mask pass still has no duration row to ask for: every `vless-ws` cell measures a *download*, where the server writes unmasked frames, so the masked direction never reaches the timer. Its evidence is the instruction count above, which is what `ops.yml` can see.

**The `?ed=` line, in gate 8.** `bench.yml` timed the shipped encode against the shape the four implementations have, on both platforms in the one run, each row byte-checked before it was timed: macOS aarch64 **3.14x / 3.10x / 3.41x / 1.99x** and linux x86_64 **2.03x / 2.54x / 2.60x / 2.11x**, at 8, 120, 256 and 2048 bytes, every row gated at 0.95x with zero allocations per encode on this side. Those are ratios against the reference's shape, not against this tree's previous body — the before-and-after for this change is the `141610` above, and this is the same-runner half that agrees with its direction.

## What we removed

- **A heap buffer for each of the two keys.** The accept key is twenty-eight bytes of base64 and the fresh key is twenty-four, and both lived on the heap: the server paid one allocation per connection to echo the accept, and the client paid one to compare it. Both are stack arrays now, coded by `b64::encode_parts_into` into the caller's own window, and the `101` and the `check_response` comparison are cut around bytes, so the accept goes out and comes back without a walk. The counting allocator is the witness: `the_keys_are_not_allocated` holds both at zero allocations. What did not move: the bytes on the wire — the RFC's example is the same accept, and the request's own key is walked once into the head's `String`, twenty-four bytes once a dial, because the early-data line is written into that `String` and the request's head is its buffer.
### The handshake that carries the `?ed=N` budget

- **Three passes over the whole head per accepted connection, and a fourth to echo a header that had already been read.** `check_request` read the request line, `Sec-WebSocket-Key` and `Sec-WebSocket-Protocol` through three functions that each ran `from_utf8` over the entire head — up to `HEAD_LIMIT`, 16 KiB — and then `accept` and `accept_split` each looked the subprotocol up a *second* time to write it back into the `101`. The references each hold the head as text once and take every field off it: Xray's `ServeHTTP` reads `request.URL.Path` and one `request.Header.Get` off the `*http.Request` `net/http` built (`hub.go:47`, `hub.go:55`) and hands the *raw* offered string to `Upgrade` (`hub.go:58`); sing-box's handler reads `request.URL` and `request.Header` off the parsed request and hands the decoded bytes to `bufio.NewCachedConn` as a buffer ahead of the connection (`v2raywebsocket/server.go:87`, `:107`); ZeroNet's `read_head` finds the delimiter in one pass, converts the head to text **once** and takes the key and the subprotocol off that string (`zero-transport/src/ws/stream.rs:351-372`). Now one `from_utf8` buys the whole handshake here too: `proxy::request_path_in` and `proxy::header_value_in` take the validated `&str`, `header_value` and `request_path` delegate to them, and `check_request` hands the offered subprotocol back in `Upgrade` so the `101` echoes the slice the first read found. The two header lookups still walked the head twice; `header_values_in` now takes both names in one line walk and stops once both are found, with `header_value_in` the one-name case. `the_two_field_walk_is_two_lookups_at_every_head` holds the one walk to the old two scans, and the probe moved **`349821 → 245757`** — `104064` fewer, 29.75% (`ops.yml` `40569939953` against `40572801264`). The bytes are pinned by `the_101_is_the_key_and_the_echoed_subprotocol`; the old-path mirror (`the_head_was_validated_three_times_over`) is still **`520242`** over the same 64 rounds.
- **A second scan for a delimiter the head reader had already stopped at.** The `Connection` path's `read_head` peeks until `head.ends_with("\r\n\r\n")` and reads exactly up to that offset, so `head[head.len() - 4..]` is the whole tail and `head[head.len()..]` is always empty — the `foxy::head_end` scan the client ran over the head to find that offset, a full SWAR pass over up to 16 KiB, bought an empty `Vec`. The bytes behind the `101` are whatever the socket still holds, so `connect` now splits with nothing behind it. The `read_exact_head` half (xhttp, httpUpgrade, the halves that cannot peek) still needs the offset, because there the read is not bounded by the delimiter.
- **A copy of every pipelined byte, and a realloc with it.** `accept_split` held the decoded early data in a `Vec` sized exactly for the digits, then `early.extend_from_slice(&prefix)` copied the pipelined frame behind the head into it — a realloc that copied the decoded bytes again and the prefix once more. Xray wraps the decoded `ed` in a `bytes.Reader` and reads the frames after it, which is the same two sources and no merge; Zray's server keeps the bytes behind the head as their own buffer (`early.rs:294`) and hands them forward. Now the prefix *is* the reader's `have` buffer: the reader already delivers `early` before it parses a frame out of `have`, so the two halves are already in the order it reads them. `the_pipelined_prefix_is_the_readers_own_buffer` proves the removal by pointer identity — the reader's base is the base of the `Vec` those bytes were already in — and `the_early_data_lands_before_the_pipelined_frame` pins the order.
- **Two `format!` buffers per handshake.** `format!` opens its `String` from the *literal* parts of the template only, so a request carrying a host, a path and a 24-byte key always reallocated at least once and copied the prefix again; the `?ed=` line then grew it a second time. Both the request and the `101` are now pushed into a buffer opened to their own length, six `push_str` calls and no `fmt::Write` in between — ZeroNet's `build_request` is the shape this drops: a `format!` per header line, each one a fresh allocation, plus a `into_bytes()` that copies the whole thing again (`zero-transport/src/ws/handshake.rs:69`). `the_request_is_sized_for_its_bytes` and `the_101_is_the_key_and_the_echoed_subprotocol` assert `capacity() == len()`, which is what "one allocation, no growth" means for a per-call buffer, over the payload lengths that are not a multiple of three (191, 192, 193) and over both sides of the budget.
- **A capacity check and a UTF-8 decision per encoded character.** `early_encode_into` pushed four `char`s per three input bytes, and each `String::push` re-derives `len_utf8`, reloads the length, the capacity and the pointer, and stores one byte. Sixty-four groups now land in a 256-byte block — one 4-byte store per group, no branch per character — and one `push_str` carries the block after one validation per 256 characters. The differential against the previous byte path still sweeps every length 0-600 (`the_windowed_load_encodes_the_bytes_the_byte_path_encoded`, raised from 520 so it crosses two block boundaries and a tail), the RFC vectors and the 0-192 round trip are unchanged, and gate 8 holds the shipped encode at **zero allocations per line** with the counting allocator while the four references' shape stays at two. The same probe reads `361968` where the four-`String::push` body reads `503578`: `141610` over 16 lines of 2048 bytes (`ops.yml` `39004141049` against `39004218090`).
- **A string the path parse built and threw away.** `EarlyData::split` opened `out` and copied the base and every kept query pair *before* it knew whether an `ed` was there, so `/tunnel`, `/p?ed=` and `/p?ed=&ed=4` — the shapes the rewrite does not fire on, and the common one among them — paid two allocations and two full copies of the path. The first `ed=` now decides and the string is built once, only when the rewrite fires, on the same `Go Atoi` arithmetic the 24 oracle vectors pin. **No checker in this tree counts that allocation**: the differential in `early_data_split_matches_go_arithmetic` and the 192-case sweep in `crates/ferrox-core/tests/parsers.rs` see the bytes and not the allocation, so the count of two-to-one is not a row here.

### The frame path

- **A read call per frame, the relay window per message, and the relay write behind them.** `Read::read` returned as soon as one message ended, so a window holding four 4 KiB frames handed the relay one 4 KiB `read` and one 4 KiB write four times. It now keeps parsing complete messages already in `have` until the caller's buffer is full; a partial next frame is left for the next call, so the ready message never waits for the socket. The relay window took the same rule later: it used to return at the first message boundary even when `have` still held the next complete frame, so a server's 8 KiB frames cost one lane step, one `writev` and one park decision apiece; it now keeps filling until the 64 KiB window is full or the lane's poll comes back empty, one retry included. For the `Read` path the copy count is unchanged — the payload still crosses into the caller once — and the socket-read count is unchanged; what falls is the `Read::read` and `read_window` returns and the relay writes behind them. The first message still waits in the transport, and only messages already buffered are coalesced. `two_buffered_frames_leave_in_one_read` hands two complete frames to one read, `small_frames_fill_one_window` hands three frames to one relay window, and `a_partial_next_frame_does_not_hold_the_ready_message` proves the second rule: a one-byte next head costs no further transport read and does not delay the first frame.

- **The relay's copy of every read byte.** The relay read a WS payload into its own `RelayBuf` and wrote from there: `Read::read` copied `have` into the caller's buffer once per byte before the socket write. The WS call sites now go through `relay_sink_ws`, whose `WindowRead::read_window` returns the frames already in `have` as spans — one per frame, headers left out — and `write_all_runs` sends those spans with a vectored write per batch, one `writev` where the socket takes the whole list and a retry over the remainder after a short call. The window itself stops at 64 KiB, so one relay write hands over at most that much; `WsReader::frame` still reads the whole frame and a masked `message` unmasks it before the first window, so the bound is on the handoff rather than on frame parsing. The remainder stays in `have` and is handed over by the next call. No byte crosses into a second user-space buffer on that path. `ws::tests::the_relay_window_is_the_readers_own_buffer` witnesses the reader-window handoff — the base is `have`'s base and the spans land on the payloads — which is the row this page counts, and `small_frames_fill_one_window` holds `have`'s pointer and capacity steady across a second window. The first window of a reader is the one that grows `have` to the window's working set (at most `WINDOW_MAX` plus one read-ahead); every window after it compacts the consumed prefix and reuses the allocation. `a_frame_larger_than_the_relay_window_keeps_its_remainder` holds the bound and the retained remainder, which stays where the first piece left it. The `Read` path is still there for sealed carried sessions and non-WS readers (`Copied`), and it still copies once; a fragmented message is delivered frame by frame, so its fragments are never packed into one contiguous run before the window is handed over.

- **An unbounded fragmented-message assembly.** `message` used to append every continuation to the bytes of the opening frame and publish the message only at `FIN`; `compact` refused to drop the consumed prefix while `assembling`, so a peer sending 16 MiB fragments with `FIN=0` grew `have` without bound before any byte reached the tunnel. The opening frame's `have` now holds each frame as it arrives and `read`/`read_window` hand its payload over before the next fragment exists, so the working set is one frame. `a_fragment_reaches_the_reader_before_the_message_fin` drives a non-FIN frame from a source that then ends: the old assembly returned nothing, the streaming reader returns the payload. Xray's gorilla `NextReader` streams the same way (`upstream/xray-core/transport/internet/websocket/connection.go:52-92`), and the 16 MiB `FRAME_LIMIT` remains the per-frame bound. What did not move: control frames are still answered on the spot, and a continuation after `FIN` is still refused.

- **An unbounded `realloc` chain in the read-ahead buffer.** `WsReader::pull` asks for `reserve_exact(READ_AHEAD)`, which requests exactly the leftover plus 32 KiB — one byte more than the previous capacity whenever the leftover grew, so a stream that lands mid-frame reallocates and memcpys once per read. `reserve` amortises that. In the good case, where a read lands on a frame boundary, the branch was already false and this changes nothing.
- **Widening the mask loop's stride the naive way is a regression; unrolling the loop over four 16-byte lanes ships.** `apply_mask` XORs 16 bytes per iteration, so about a quarter of its work on a long masked frame is loop counter and bounds check rather than XOR. Striding 64 bytes was tried — same vector op count, same bytes at the same offsets, since 64 is a multiple of the 4-byte mask — and it is a **regression**, and the arithmetic says so without a benchmark: the remainder is taken scalar, so `as_chunks_mut::<64>()` makes the scalar tail up to 63 bytes where `as_chunks_mut::<16>()` kept it under 16. At 63 bytes it is 63 scalar XORs against 3 vector ops plus 15. Every length that is not a multiple of 64 is worse, and the lengths that are multiples of 64 are unchanged, so the change only ever helped frames that were already vector-aligned. Reverted. What ships instead keeps the 16-byte op and strides the *loop* 64: four `xor_block` lanes per iteration, the sub-64 remainder through the old 16-loop, scalar tail still under 16 — same vector ops, a quarter of the loop overhead, identical tail by construction since 64, 16 and the tail start are all multiples of the 4-byte mask. `mask_chunks_match_the_byte_loop` pins it against the byte loop at every 16- and 64-boundary ±1.
- **Two read syscalls per message, unconditionally, forever.** The old `frame_head` called `read_exact` for 2 bytes, then `read_exact` again for the extended length and the mask, then `read_exact` for the payload. Comparing the three implementations: Xray uses gorilla/websocket with a **4 KiB** read buffer, so it spends roughly one syscall per 4 KiB and splits every 8 KiB payload across two buffers and two writes; sing-box uses `sagernet/ws` over a 32 KiB `buf.Buffer`; Zray reads into `read_buf`'s spare capacity with `ReadBuf::uninit`, then `split_to`s the frame out — a view, not a copy. Three syscalls for a 14-byte header is worse than all three, and the new `a_read_covers_a_window_not_one_frame_header` drives the reader over a fixed byte source, where a `read` returns everything it is asked for, and asserts that 64 frames of 21 472 bytes cost exactly **one** read.
- **The `unsafe { set_len }` that zero-filled first.** The old `data_into` grew the backlog with `reserve` + `set_len`, which is right, but the buffer was then cleared and refilled per message. `pull` keeps one buffer sized once per connection and grows it only when a single frame needs more room than the window holds — a 16 MiB frame costs one `reserve_exact` and then no compaction.
- **A second buffer.** `backlog`/`bat` and `have`/`at`/`msg_end` were two ways of holding the same thing; there is now one, which is both smaller and one fewer place for a copy to hide.

- **Half the instructions per masked byte, on every `avx2` host.** The masked pass walked sixteen bytes with a load, an xor and a store, and the sixteen above it with three more of the same, so the arithmetic of the loop was fixed at three instructions per sixteen bytes however long the frame was. One `ymm` does the same work over thirty-two, still three instructions, which is why the rung is a dispatch on `std::is_x86_feature_detected!("avx2")` above a buffer of at least one pass, with everything else — including every byte past the last whole pass — still through the old ladder. The bytes do not change: xor has no width. `ops.yml` read `ws::tests::the_masked_frame_costs_the_walk_over_its_payload_and_nothing_else` at `330417` before the wide pass and `294378` after: **−36 039 Ir, −10.9%** for the same 16 rounds of the relay's 16 KiB chunk. The mask loop's own probe, `ws::tests::mask_chunks_match_the_byte_loop`, moved `452984` → `437971`, and `ws::write_frame`, which is driven over a loopback socket and so moves between runs, moved `168227` → `150445`. All three are in the same direction, and the two in-memory rows are the ones to read.

What is unchanged, deliberately: the **aarch64** step stays 16 bytes per `xor_block` with a tail loop, mirroring Zray's measured `u128` step ("Measured on Apple Silicon at opt-level = s, 1 KiB 121 → 71 ns and 16 KiB 1189 → 793", with a note that a 32-byte step is slower because four stores into one cache line each wait on the three before them). That measurement is the reason the NEON rung does not widen — 128 bits is the whole vector width there, so a wider pass is more stores per byte, not fewer, and SVE is not baseline anywhere this tree ships to. The same note does not cover the x86 rung, where one `vmovdqu` of a `ymm` replaces two of `xmm`. sing-box's `ws.Cipher` uses an 8-byte `uint64` step; that is a regression against the measurement Zray published, so it was not copied.

- **The masked-write staging copy and the mask walk are fused into one pass.** The old writer did `frame.extend_from_slice(data)` — a libc `memcpy` of the payload, read and write — and then `apply_mask(&mut frame[base..])`, a second read-modify-write over the same bytes: four touches of memory per payload byte. `mask_copy` walks the caller's `&[u8]` through the *same* `ymm`/`xor_block` rungs that unmask in place, reading each byte once and storing its masked byte once, so the frame costs two touches at identical bytes — the xor has no width and the mask phase is unchanged because every stride is a multiple of four. What an earlier note here called a floor ("`memcpy` for the copy retires in libc's own frame, so the fused version puts work *into* the counted frame and reads worse") assumed a fold built on `memcpy`; this one replaces the libc frame with the ladder already in the tree, so there is no separate walk to pay for. `ws::tests::the_fused_fill_is_the_memcpy_then_mask_byte_for_byte` pins the fold against the byte loop at every rung boundary, staging base and mask; `the_masked_frame_costs_the_walk_over_its_payload_and_nothing_else` holds `MASKED_FRAME`'s capacity steady across the rounds, so the fusion touches no allocator. The copy count stays `1` — the payload still crosses into the frame once — and it is the removed *second pass* that the instruction row prices; that row is read from the CI `ops.yml` artefact, and the local `count-ops` gate that could see it is CI-only on this macOS/aarch64 host (no `valgrind`), so no figure is pasted here.

## What is not removed, and where

- **The decoded early data is still a fresh `Vec`.** Xray's server decodes into `ed` and wraps it in a `bytes.NewReader`, and Zray decodes into the `early` field of its stream; both allocate what they return. Folding it into the reader's `have` instead would need the pipelined bytes *prepended*, which is the merge this slice removed.
- **The `?ed=` budget is still parsed per configuration**, not per connection — `resolve_ws` and `resolve_httpupgrade` call `EarlyData::split` while the config is read. What the rewrite removes there is the second allocation and the rebuild, not a per-connection cost.
- **The masked-write staging copy itself stays**, fused into the single ladder pass above — the payload still crosses into the frame once — and the aarch64 mask step stays 16 bytes for Zray's published reason.
- **The `Read` path still copies once.** Sealed carried sessions and any relay whose reader is not a `WsReader` go through `Copied`, which reads into a `RelayBuf`; that payload crosses into the relay's buffer once. Only the WS relay moved to the window.
- **A frame is still read whole before its payload is delivered.** `frame` waits for the header and the complete payload (up to `FRAME_LIMIT`, 16 MiB) in `have`; the streaming bound is per fragment, not per byte. A control frame interleaved between fragments is answered on the spot and does not hold the fragments already whole.

## CI scope

What a change here owes, read by `scripts/ci-scope.py`; see [`docs/ci-scope.md`](../ci-scope.md). The `?ed=N` codec itself is **not** claimed by this page's `paths`: `EarlyData`, `early_encode_into` and `early_decode` live in the shared `crates/ferrox-core/src/transport.rs`, which `early_encode_into` also reaches from `proxy.rs::b64url` for a REALITY x25519 key. So a hunk in that file keeps the plan wide — the whole matrix, both roles' suites — and a hunk in `ws.rs` alone narrows to `vless-ws`. Claiming the codec here would narrow a future edit to one carrier and hide that second caller, so the wide plan is what a change to the codec costs.
