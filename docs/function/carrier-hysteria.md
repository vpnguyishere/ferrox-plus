# The Hysteria carrier

Hysteria is a **both-roles, both-shapes** row, carrying the reference's v1 binary protocol and its v2 HTTP/3 protocol behind the same `hysteria` transport name. For v2, as the transport it dials from a SOCKS inbound without Mux and serves a `streamSettings` inbound whose whole `tlsSettings.certificates` list it hands to BoringSSL — the client's SNI picks the entry; with `rejectUnknownSni` off an absent name answers the first, and with it on an absent or unmatched name is refused (`hysteria_serves_the_certificate_the_sni_names`; the shared builder's refused-absent gate is `quic::tests::a_hello_without_a_name_is_refused_when_the_list_rejects_it`) — carrying the inner protocol (VLESS or Trojan) on each `0x401` stream; a Trojan flow sends no acknowledgement and its UDP association rides the lane's own SOCKS frame, gated by `hysteria_carries_trojan_echo_over_loopback` and `hysteria_carries_a_trojan_udp_association_over_the_carrier`. The dial's QUIC TLS takes its SNI from `tlsSettings.serverName`, falling back to the address only when the config names none, while the auth request's `:authority` is the protocol constant `hysteria` — the reference's `URLHost` — not the SNI; `vless_with_hysteria_takes_tls_as_the_carriers_own_handshake` pins the SNI mapping and `an_auth_request_carries_post_auth_and_the_brutal_hint` the authority and the hint, so the matrix's `carrier.test` certificate and the `hysteria` auth host are checked apart. As the protocol it serves a `protocol: hysteria` inbound: the stream's request itself names the destination as a varint string, the server acknowledges before it dials, and a refused dial closes after the acknowledgement. Both run over quiche — the default QUIC stack for this rung, pinned at `upstream/quiche` for reading. Every served v2 connection also carries the QUIC datagram lane: the auth response advertises `hysteria-udp: true` the way the reference does whenever a validator is present — and a served connection always has one — so the lane is on rather than negotiated, and no branch of it is dead config. An inbound that names `tlsSettings.obfs: salamander` masks every datagram of that lane: an 8-byte random salt then the QUIC packet XORed against `BLAKE2b-256(password || salt)` tiled at `key[i mod 32]`, applied at the `quic::Datagram` seam so no handshake, frame or stream above it changes. Salamander is the only v2 mask carried, and `gecko` is the one variant that rides on top of it; any other named obfs, or a password below the 4-byte floor the reference accepts, is refused as `Unknown` rather than silently sent in the clear. The masked lane is proven end to end by `hysteria_carries_a_flow_through_salamander_over_loopback` — the same dial-and-echo path as the cleartext gate, over a salamander socket on both ends, which only completes if the salted seal and the in-place unmask agree.



On Linux the v2 lane hands a whole relay window to the kernel in one call and takes a coalesced burst back in one read: `send_batch` writes up to `SEND_SLOTS` packets as one `UDP_SEGMENT` datagram (capped at `GSO_SEGMENTS` so the burst stays under the 65507-byte UDP ceiling), falling back to `sendmmsg` when a short packet or a moved peer breaks the run, and `recv_batch` cuts a `UDP_GRO` burst back into the packets quiche reads. The served router answers a batch with `quic::flush_egress`'s one sweep — one `sendmmsg`, or one `UDP_SEGMENT` message for a full run — rather than one `send_to` per datagram, which is what lets the server leg carry an upload at the client's rate; `the_lane_sends_the_datagram_its_buffer_holds` and `a_gso_burst_arrives_as_its_segments` are the loopback gates, and the batch is only taken when the socket names it, so a non-Linux lane keeps the per-packet path.

Hysteria **v1** is the binary handshake the reference shipped before v2: `version: 1` selects it, the first client-bidirectional stream (0) carries a `ClientHello` — one version byte, the two `BE64` rates and the auth — and the server answers `ServerHello` on the same stream before any flow opens. A TCP flow is stream 4, 8, 12 … with a `ClientRequest` (`UDP` flag, `BE16` host length, host, `BE16` port); the server writes `ServerResponse` (`ok`, `BE32` UDP session id, message) and relays raw bytes. The UDP lane is one flow stream per association whose `ClientRequest` names `UDP=true` and the first destination, and whose datagrams carry the session id, each packet's own destination host and port, a packet id and `fragID`/`fragCount`/length — the whole shape owned by `ferrox-core::hysteria_v1` and pinned bit-exact by `a_client_hello_is_the_exact_bytes_the_reference_emits`, `a_server_hello_and_response_are_the_exact_bytes_the_reference_emits`, `a_client_request_is_the_exact_bytes_the_reference_emits` and `a_udp_message_is_the_exact_bytes_the_reference_emits`. Fragmentation and reassembly are the same core codec's `fragments_udp`/`Defrag`, swept over every length 1..=200 (`hysteria-v1-fragments-witnessed` 200, `every_length_survives_fragment_then_defrag_intact`). v1 has no HTTP/3 auth, no `hysteria-udp` header and no masquerade: a right-shape wrong password is refused in the `ServerHello` and the connection closes, which `hysteria_v1_refuses_a_wrong_password_without_relaying` gates. Its obfuscation is **xplus** — a 16-byte random salt followed by the QUIC packet XORed against `SHA-256(password || salt)` tiled at `key[i mod 32]` — not salamander; `the_xplus_mask_matches_an_independent_sha256_computation` pins the transform against an independently computed keystream, and `Datagram::xplus` applies it at the same `quic::Datagram` seam v2's salamander uses, so no handshake, stream or datagram above it changes. The v1 inbound reads users' `settings.users[].auth`, the whole certificate list from `tlsSettings.certificates`, selected on the SNI the same way (`hysteria_v1_serves_the_certificate_the_sni_names`), and now the same `udpIdleTimeout` and `finalmask.quicParams` through the one `hysteria_v1_config` the dial also builds, so a `version: 1` server reaps on its configured bound and its QUIC lane takes the block; the v1 outbound reads `settings.version: 1`, the first server's address/port/auth, and the same stream settings. The matrix's `hysteria-v1-down-8` cell runs this standalone shape on the ferrox server with sing-box as the reference, because xray-core reads v2 only. Both roles are gated end-to-end over loopback: `hysteria_v1_carries_a_tcp_echo_over_loopback` and `hysteria_v1_carries_a_udp_echo_over_loopback`. Brutal maps to quiche `bbr` exactly as v2 does, and a config naming neither version 1 nor 2 is still `Unknown`.

The v2 wire shape is small: every TCP flow is one client-bidirectional QUIC stream opening with the `0x401` varint, and the connection opens with an HTTP/3 `POST` to `/auth` carrying `hysteria-auth`, answered `233`. `ferrox-core::hysteria` owns those bytes and proves them bit-exact (`ferrox-core-hysteria::*` unit tests); `ferrox-app/src/hysteria.rs` owns the sockets: a `Router` keyed by server SCID on the serve side, and on the dial side one authenticated connection per outbound, pooled and reused for every flow it can carry — stream 4, 8, 12 … — the way the pinned client multiplexes (`max_tcp_streams: 64`; this tree caps at quiche's `MAX_STREAMS`). The datagram lane rides the same pooled connection: on the serve side one association per `BE32 session` id, keyed in the route's table, relayed to its connected target socket through `ferrox-core-hysteria`'s codec (`decode_udp` borrows the payload out of the arrived datagram; `a_decoded_datagram_leaves_its_payload_where_it_landed` is the pointer-identity witness), reassembled by `Defrag`, and reaped after `udpIdleTimeout` (60 s when the stream names none, the reference's default) or the connection's close — a UDP socket has no shutdown to wake a blocked read, so the reply-path reader threads end on the `UDP_POLL` (1 s, the reference's cleanup tick) timeout watching the stop flag the reap sets. The dial side answers that lane in its own small shape: `serve_udp` relays a socks5 UDP association over a connection of its own — the pool is a TCP instrument, and a stale connection carries a datagram into a silent blackhole with no reply deadline to catch it — one destination at a time, each stamped with a session id the connection never reuses, the writer holding the connection lock once per datagram and a companion reader driving it with `drive_once` — so the client's UDP flows are this carrier's row, not a cross-cutting gap: `hysteria_udp_lane_carries_a_datagram` witnesses the lane off the front and `hysteria_carries_a_udp_association_over_the_carrier` through the full socks dispatch. A pooled connection is reused within half the server's 300 s idle timeout, dropped when it stops taking application data (closed, draining or carrying a close), goes stale or runs out of streams, and a dial with no live pool entry pays a fresh handshake: `hysteria_shares_one_connection_between_two_flows` witnesses one handshake carrying two echoes on the `HANDSHAKES` counter, and `hysteria_redials_when_a_pooled_connection_closes` the fresh handshake after `close_pooled`.

A wrong password is refused with `404` then `CONNECTION_CLOSE` and relays nothing: `hysteria_refuses_a_wrong_password_without_relaying` is the gate. Settings parse with guarded fallbacks — unknown congestion spellings pace as `bbr`, and `version: 1`, `version: 2` or absent names this carrier, anything else is `Unknown`: `hysteria_settings_parse_with_guarded_fallbacks` is the gate. The full path, dial plus auth plus one VLESS echo, is `hysteria_carries_vless_echo_over_loopback`, and the UDP lane's full path — advertisement, association open, fragment, defrag, target echo, reply frames — is `hysteria_carries_udp_echo_over_loopback`, both serialised on the shared QUIC mutex and retried like the other loopback socket tests, because a socket test that passes twice and fails the third is testing the scheduler. The protocol shape's gate is the pinned one: `xray-rust-hysteria` in `upstream/pins.toml` runs the pinned client's wrong-password and failed-destination verdicts against `ferrox-app` in `scripts/run-upstream-suite.sh`, which is also where the server's SETTINGS-before-auth order is proven — the pinned client's H3 stack posts its auth only once the server's SETTINGS arrive.

Both roles read the reference's lane tuning, `hysteriaSettings.udpIdleTimeout` and `finalmask.quicParams`, with the reference's own bounds and defaults: `udpIdleTimeout` sets the association reaper's idle bound (absent or 0 is 60 s; outside 2..=600 the carrier is refused), and `quicParams` sets the QUIC idle timeout (a field the block leaves out, or names 0, is 30 s; 4..=120), the four receive windows (a field left out is 8 MiB per stream and `8 MiB × 5/2` per connection, never below 16 384), the initial incoming streams (left out is 1024 on a serve, 8 minimum when named), `disablePathMTUDiscovery` (`discover_pmtu(false)`), the client's `keepAlivePeriod` (2..=60 s, 0 off) and `disableStatelessReset`, which suppresses the token a serve otherwise advertises — minted fresh for each accepted connection, never shared from the template (`a_stateless_reset_token_is_minted_afresh_per_accept`, `a_disabled_stateless_reset_sends_no_token`). The congestion names are the reference's — `reno`, `bbr`, `brutal` (the default), `force-brutal` with `brutalUp` required — a present block owns the congestion even when it names none, and the tree's extra `hysteriaSettings.congestion` applies only when the block is absent; a stream with no `quicParams` at all keeps the lane this tree shipped — 300 s idle, 4 MiB stream and 16 MiB connection windows, 100 streams — and advertises the reference's per-connection stateless-reset token, where a present block is the reference's lane with its own fills; `brutalUp`/`brutalDown` take the reference's units (`"10 mbps"`, or a bare number as bits per second) with its 65 536-byte floor; the configured `brutalDown` rides both auth directions as `Hysteria-CC-RX`, so an xray-core peer in Brutal mode caps its send rate at it. A tuned `quicParams` is its own pool key, because its windows and idle bound were negotiated: `a_hysteria_carrier_reads_the_udp_idle_and_the_quic_params` gates the read, the empty block, the defaults and every refusal outside these bounds, `a_datagram_association_reaps_on_the_configured_idle` pins the reaper to the configured bound rather than the fixed default (a six-second-old association dies at five seconds and lives at sixty), `a_v1_datagram_association_reaps_on_the_configured_idle` pins the v1 server's reaper the same way, and the key is `a_quic_tuned_plan_is_its_own_pool_key`. Two gaps are named rather than closed: `bbrProfile` is accepted and validated like the reference's but changes nothing, because quiche's custom-BBR knobs are behind an internal-only feature — stock BBR2 stands — and `keepAlivePeriod` is applied client-side only, as the reference does — its dialer hands quic-go a keep-alive period while the server's QUIC config leaves it zero — the period riding the driver as an ack-eliciting packet only when nothing new was sent.

A browser that stumbles on this port with a plain `GET /` is answered rather than refused: the masquerade site serves an ordinary HTTP/3 request on the *same* connection hysteria rides. The classifier is a stream's first varint — `0x401` names a hysteria flow and relays as before, while an HTTP/3 `HEADERS`/`DATA` frame (`read_tcp_prefix` returning `None` beside those types) is a browser and goes to `serve_masquerade`; on stream 0 the same split keys on request shape — a `POST` to `/auth` is the handshake and anything else is the cover — proven apart by `the_flow_frame_tells_hysteria_from_a_browser_request` and `a_browser_get_parses_to_method_path_and_authority`. Four cover answers match the reference's `masq` — the default `404` page, a canned `response` line, a static `file` directory and a `proxy` to an origin — every one built by `ferrox-core::hysteria`'s `encode_h3_response` (a `HEADERS` frame then a `DATA` frame) so the bytes are pinned without a socket. A right-shape, wrong-password hysteria attempt still refuses with `404` and closes exactly as a plain server would (`hysteria_closes_a_wrong_hysteria_password_even_with_masquerade`), so the cover never walks past authentication, and a browser `GET` beside a live flow is served while that flow still relays (`hysteria_still_carries_proxy_flows_beside_a_masquerade_get`).

A dial whose `hysteriaSettings` names `serverPorts`/`mport` (a comma spec or an array of ports and `start-end` ranges) and `hopInterval`/`hopIntervalMax` **hops its server port**: the destination moves among the expanded set every random stay, and the socket moves with it — a fresh local bind per move, so a filter or NAT sees a new flow rather than one long-lived one, the way the reference's `HoppingSocket` does. It lives at the same `quic::Datagram` seam as salamander, so only the destination port and the socket change and no handshake, frame or stream above is touched; a salamander seal still rides each hopped datagram. The plan is expanded, deduplicated and sorted once per dial in `ferrox-core::hysteria` (`Hop::ports`, `hop-port-set-expanded` 4 witnessed by `the_plan_expands_overlapping_ranges_into_one_sorted_set`), and the two decisions — never land back on the port just left (`pick_next`) and draw the next stay inside its window (`stay_ms`) — are pure functions of the port set, the port to avoid and one folded-in roll, so they are proven without a clock or an rng. The wire keeps one view of the peer: only the server's own address is rewritten, a datagram to any other target passes through, and a reply from any hopped port is turned back to the nominal port the connection was named for (`is_hop_port`) so QUIC above keeps accepting it — `hopped-reply-source-normalized` 1 witnesses that rewrite off a loopback listener, and `hopped-datagrams-delivered` 200 that a zero-millisecond schedule spreads a burst over more than one port with none lost. The old socket lingers ten seconds for its in-flight replies, and the plan joins the pool key (`hop-plan-pool-keys` 2: `a_hop_plan_is_its_own_pool_key`) so a hopped dial never rides a plain connection to the same address, nor the reverse.

An inbound that names `tlsSettings.obfs: gecko` fragments **and** masks: gecko is a fragment-plus-pad layer composed on top of salamander, so it shares the salamander key and the same `quic::Datagram` seam. A QUIC long-header packet (first byte `& 0x80`) is split into 2..=8 chunks, each wrapped in a 5-byte frame (`0x80`, a message id, `chunk<<4 | total`, a big-endian pad length) plus random padding drawn so the salamander-masked datagram — `salt(8) + frame(5) + pad + chunk` — lands inside a `[min, max]` window (defaults 512..1200, cap 2048), then sealed exactly as a plain salamander datagram; a short-header packet is masked whole and passes through. The receiver reassembles by `(peer address, message id)` — the port is left out because a hop opens a fresh socket per stay, so one split message can arrive from several source ports. The frame codec — `encode_gecko_frame`, `decode_gecko_frame`, `gecko_chunk_range`, `gecko_pad_len` — is pure `ferrox-core::hysteria` and proven bit-exact: the exact emitted bytes (`gecko-frame-bytes-encoded` 10, `a_gecko_frame_is_the_exact_bytes_ the_reference_emits`), a decode that borrows its payload out of the input with no refill (`gecko-frame-decode-copies` 0, pointer-identity), a forged or truncated frame refused with the buffer held, and a 1234-byte packet that fragments and reassembles byte-identical (`gecko-packet-reassembled-bytes`). The window parses from the sing-box `min_packet_size`/`max_packet_size`, their camel spellings, or the reference's `packetSize` range as an object or a two-element array (`gecko-window-forms-parsed` 3), and an unusable window is refused rather than carried as a plain salamander that would silently drop the fragmentation. A dial that both hops the port and geckos the framing composes the two: the fragmenter seals and pads each chunk and writes it through the hop's current socket, so the port rotates under a message the receiver still rebuilds — `a_hopped_gecko_dial_sends_its_fragments_over_more_than_one_port` witnesses the fragments leaving on more than one port inside the window, and `a_hopped_gecko_dial_reassembles_at_a_plain_gecko_peer` the split packet coming back byte-exact through the hop. The whole split-and-reassemble round trip over a real loopback socket is `gecko-loopback-reassembled-bytes` 900 (`a_gecko_dial_reassembles_its_split_long_header`), which also witnesses that a long-header packet leaves the socket as more than one padded datagram.

## What we removed

- **A second certificate reader, and a temp file to feed it.** Hysteria had its own `tls_cert_paths`, which read one file-backed pair and handed quiche PEM through a staged temp file; both versions now share the TLS inbound's `tls_identity_from_settings`, so an inline `certificate`/`key` and the whole `certificates` list work here exactly as they do on `security: tls`. `a_carrier_that_owns_tls_reads_the_same_certificate_list` gates the parse (two entries, two chains), `hysteria_serves_the_certificate_the_sni_names` the v2 serve over a real handshake, and `hysteria_v1_serves_the_certificate_the_sni_names` the v1 serve. What this removes, named: the file staging and its PEM pass from the serve path, and the second config reader; what it does not remove is the DER parse BoringSSL still does for each entry.
- **The v1 protocol's own transport stack, rewritten smaller.** The reference v1 client and server keep a full congestion controller, an auth manager and a separate packet codec; this tree carries only the binary handshake, the request and the datagram shape in `ferrox-core::hysteria_v1`, reusing quiche and the existing `Flow`/`Datagram` seams. v1's xplus mask is one `SHA-256` keystream over the caller's datagram rather than a second socket layer, and its fragmentation is the same `Defrag` the v2 lane uses. What remains: v1 has no masquerade, no HTTP/3, and no `hysteria-udp` advertisement, because the reference v1 has none.
- **The upstream UDP session machinery, rewritten smaller.** Both pinned implementations keep a UDP session manager with a per-direction message channel beside the streams (`conn.go:udpSessionManager`, `protocol/hysteria2` inbound/outbound UDP paths). This tree carries the lane as one `UdpFlow` per association — a connected target socket, the `Defrag` reassembly, and the idle reap — the parse, fragmenter and reassembly living entirely in `ferrox-core::hysteria`, proven by `every_length_survives_fragment_then_defrag_intact` (the 200-row sweep is `udp-fragments-witnessed`) and end to end by `hysteria_carries_udp_echo_over_loopback`, and on the dial side smaller still: one `Association` and one shared `Lane` per socks front — no manager, no channels, the reader a single thread riding `drive_once` — proven by `hysteria_udp_lane_carries_a_datagram` and `hysteria_carries_a_udp_association_over_the_carrier`. The reference's `MaxDatagramFrameSize: 1200` is not reimposed; fragmentation sizes to the peer's live `dgram_max_writable_len` instead.
- **The decoder's per-datagram payload copy.** The relay hands `decode_udp`'s borrowed payload straight to the target socket's one `send`; the pointer-identity test pins the base inside the arrived datagram, the buffer unmoved, the capacity ungrown (`udp-datagram-decode-copies` 0). - **An address copied and a payload staged to hand a whole datagram on.** `Defrag::feed` answered every whole packet with a `(String, Vec<u8>)` it built itself — `message.address.to_owned()` and `message.payload.to_vec()` — even when `frags == 1` meant no reassembly at all, so the common datagram paid two allocations and two copies before the relay put the bytes back into its own buffer. The answer is now borrowed: `feed` hands the message's own `&str` and `&[u8]` for a whole packet and takes a buffer to assemble into only for the fragmented case, where the pieces are not contiguous. `an_unfragmented_datagram_is_handed_over_without_a_buffer` pins both bases against the message's (`udp-datagram-reassembly-allocations-per-whole-packet` 0) and holds the window over 4096 feeds — 0 allocations, 0 bytes, 0 zeroed; staging the payload back into the answer turns the pointer assert red. What the lane still pays, named: quiche's `dgram_recv_buf` still returns the datagram as an owned `Vec` (one copy per arrival, inside quiche), the fragmented path still keeps one `Vec` per slot until assembly, and the client-side relay still copies the payload once into the socks5 reply frame because the header and the payload leave as one `send_to`.

- **A second delimiter walk in the origin-response parse.** `parse_origin_response` opened with `windows(4).position`, the four-byte weigh at every offset, and now reaches `foxy::head_end` — the tree's one eight-byte-at-a-time scan — so an origin's head is found the way this lane's own CONNECT answer finds it. The offsets and the `None` are unchanged, gated by `the_swar_terminator_scan_is_the_windows_four_scan` on [`carrier-foxy`](carrier-foxy.md); what the lane still pays is the rest of that parse, one `split` per header line.

- **Salamander's pre-allocated key buffer and separate output.** Both references build `password || salt` into a fresh slice, hash it, then write a new masked buffer. This tree streams the two parts into one `BLAKE2b` update so the concatenation is never materialised, and the wire form `seal_into` writes salt-then-mask straight into the caller's datagram frame — `a_sealed_datagram_never_touches_the_heap` pins that frame's base and capacity across a fresh salt (`obfuscated-datagram-heap-copies` 0), and `the_stack_seal_form_matches_the_vec_oracle_form` proves the in-place form emits the same bytes as the `Vec` form the oracle vectors pin. What the lane still pays, named: the salt itself costs one `getrandom` per datagram, which is the construction, not overhead, and a receive room narrower than `RECV_ROOM` still takes the scratch-and-copy path named in the bullet below.
- **The inbound unmask's copy back.** A masked read used to land in a scratch a salt wider than the caller's buffer, unmask there, and copy the plaintext back. Every receive room that can see a masked lane is `RECV_ROOM` now — a datagram plus the widest salt — `drive_once`, the queue behind its first datagram, the server's `serve_loop` and the quic carrier's `pump_once`, so the read lands in the caller's own buffer and the unmask happens where the bytes did: one copy per received obfuscated datagram retired, and the scratch buffer it replaced is gone, leaving one room 16 bytes wider where there were two. `an_obfuscated_read_unmasks_where_the_wire_bytes_landed` sends a frame sealed under a known salt and pins the salt-wide tail the shift never reaches against the frame's own masked end — a copy out of a scratch leaves the caller's sentinel there and turns the assert red. `an_obfuscated_lane_round_trips_a_full_datagram_over_loopback` keeps a `MAX_DATAGRAM` room and so still takes the scratch path, which is the fallback a narrower caller keeps. What is not removed: a relay-framed read still shifts its header off with `copy_within`, and a caller that passes less than `RECV_ROOM` still pays the copy.
- **The mask's byte-at-a-time XOR and its in-place scratch.** `Salamander::obfuscate_into` and `deobfuscate_in_place` walked the payload one byte at a time, each step re-reading the keystream at `i % 32` behind a bounds check. Both v2 and v1's `XPlus` now share `ferrox_core::keystream`: the keystream is the key's own 32 bytes, so one step XORs both sixteen-byte little-endian words of the key (a NEON `eor` or SSE-derived vector XOR after lowering, and the byte xor either way), covering the whole key phase with no modulo in the body. The unmask moves the payload toward the front by the salt's length; a step loads its source word before storing below it, and every later source begins past that store, so a salt of eight or sixteen bytes needs no scratch block at all — the 32-byte stack round trip per block is gone. The bytes did not move, gated by `every_length_unshifts_like_the_byte_walk` and `encrypt_and_apply_agree_at_every_length` (every length 0..=200 at both shifts), `the_stack_seal_form_matches_the_vec_oracle_form` (1, 32, 33, 1342) and `salamander_round_trips_every_length_under_a_fresh_salt` (1, 7, 31, 32, 33, 63, 64, 1200, 1342) against the byte-wise `Vec` oracle form. No `Ir` row prices this: `ops.yml` reports `Salamander::obfuscate_into` and `Salamander::deobfuscate_in_place` both `inlined-not-a-frame`, and the matrix cell that measures this lane is cleartext, so the mask is not in its path. What is not removed: an inbound obfuscated datagram still pays the scratch-and-copy on the quic seam named above when the caller's room is narrower than `RECV_ROOM`.
- **The masquerade site's web-server machinery, rewritten minimal.** The reference answers `masq` with a real `net/http` stack — a `Server`, virtual hosts, `http.FileServer` with its full `os` walk, and an `httputil` reverse proxy pooling origin connections. This tree hand-rolls the same four cover answers off its own H3 codec: `serve_file` sanitises the `:path` (percent- decode, reject any `..`/escape) against one root and answers with a content-type read off the extension; `serve_proxy` speaks a hand-written HTTP/1.1 request/response over the existing transport seam, drops the hop-by-hop headers, de-frames a chunked origin body in core (`a_chunked_origin_body_defragments_to_its_bytes`) and buffers it under the datagram cap. No server object, no pooling, no new dependency — `masquerade-file-bytes-served`, `masquerade-proxied-round-trips` and `masquerade-escapes-served` 0 pin the file, proxy and traversal paths, and `masquerade-answers-browser-on-same-port` pins the canned answer reaching a browser on the port hysteria dials. An `https` origin wraps that same hand-written exchange in `ferrox_core::tls::connect` — the client TLS the relayed lane already speaks — so the cover adds no second TLS stack and no dependency; `masq_url_insecure` is honoured by one accept-as-presented verifier reachable only from this path, and `masquerade-https-origin-served-bytes` 6 and `masquerade-https-untrusted-refusals` 1 pin that a named-insecure chain serves and a verified dial against an untrusted chain refuses rather than silently trusts. All three schemes now resolve to one `crate::conn::Target`, so the cover dials `http`, `https` and `unix` origins through the same seam the relayed lane rides, and `ORIGIN_TIMEOUT` now bounds every leg of the exchange: the connect gets the bound the read already had, so an origin a firewall pins answers the bad-gateway line in five seconds instead of parking the stream handler for the kernel's own retransmission (a socket path answers its own connect at once, so its budget is the read's), and the request write gets one too, so an origin that accepts but never reads cannot hold the cover open either. `masquerade-unix-origin-served-bytes` 6 dials a real socket path and gets the answer byte-identical to the TCP origin's, which is what witnesses the unix scheme on the seam rather than beside it.
- **The hopping socket's async machinery, rewritten to a synchronous schedule.** The reference's port hop is an async `HoppingSocket` wrapping a quinn `AsyncUdpSocket`, with a spawn/replace dance per hop and a `GenRng` threaded through. This tree keeps the same three facts — never the port just left, a stay drawn inside its window, the old socket read until its linger expires — as two pure core functions and one `Mutex<HopState>` behind the existing blocking `Datagram`, so hop, obfs and the relay share the one seam rather than a parallel socket type. No new task, no rng type, no second socket: `pick_next`/`stay_ms`/`Hop::ports` are proven without a socket at all.
- **The hop plan's squares and double walks.** `Hop::ports` paid one linear `contains` per new port over a growing `Vec`, `pick_next` filtered the set twice and walked it a second time to land one index, and `is_hop_port` scanned the whole plan for one reply's source on every datagram. The expansion now opens one buffer sized to the ranges' total capped at the distinct-port ceiling (65 536) and sorts once with `dedup`, `pick_next` binary-searches the avoided port's place and lands the roll with one modulo and one skip, and membership is one binary search — all three over the one sorted distinct set `Hop::ports` hands out. The bytes did not move: `every_plan_expands_to_the_bytes_the_contains_scan_wrote` sweeps empty, single-port, overlapping, out-of-order, inverted and wide range sets against the contains scan kept as the oracle and holds those measured plans whose pushed total stays under the ceiling at one allocation (`hop-port-expansion-allocations` 1), `every_pick_lands_the_survivor_the_two_filters_walked_to` sweeps six sets against six avoided ports over two hundred rolls, and `every_membership_reads_as_the_linear_scan_read_it` sweeps a four-port and a thousand-port set against the linear scan. What was **not** removed, named: the reserve caps at the 65 536-port ceiling, so a plan whose pushed ports outrun it can pay further growth before `dedup` — three identical full-port ranges push 196 608 entries before any duplicate is removed — rather than a buffer sized for every duplicate, and no allocation count is claimed for such a plan; and the binary forms take the sorted distinct set as their contract (`# Contract` on `pick_next` and `is_hop_port`: strictly ascending and distinct, as `Hop::ports` returns and `Hopper::open` restores), so a caller handing them an unsorted duplicate list is outside it — it panics in debug builds via the `debug_assert` and answers wrongly without error in release.
- **Gecko's background expiry thread.** The reference reassembles fragments in a map swept by a dedicated `gcLoop` timer goroutine that ticks to expire stale messages. This tree keeps the same three facts — an 8 s TTL, a per-source cap and a global cap — but drops the thread: each `accept` runs one `retain(|_, m| m.until > now)` over the table it already holds behind its `Mutex`, so an expired message is swept lazily on the next frame rather than by a ticker that wakes with nothing to do. No task, no timer, one owner for the map: `gecko-loopback-reassembled-bytes` witnesses a split long-header round-tripping byte-identical over a real socket, and `gecko-packet-reassembled-bytes` the same reassembly purely in core.
- **A custom brutal sender.** `brutal` and `force-brutal` pace as quiche `bbr` (`Congestion::quiche_name`), stated in the settings test. That is a narrower congestion loop, not a second implementation of one. What the reference would switch to instead is its own Brutal pacer once both rates and the peer's hint are present; this tree keeps quiche's `bbr` and sends its configured `brutalDown` as the `Hysteria-CC-RX` hint in both auth directions, so an xray-core peer in Brutal mode caps its own send rate at it, and a peer that names no rate sees the hint carry `0` — no cap, the reference's own spelling.
- **Rate-capped pacing.** `brutalUp`/`brutalDown` are read and validated — the reference's units, its 65 536-byte floor, `force-brutal` needing an up rate — and the down rate rides the auth headers as above, but this tree does not pace by them: flows pace by quiche `bbr` uncapped, which is wire-compatible with a capped peer and differs only in throughput. v1's hello rates are fixed at 100 Mbps on both sides for the same reason: the fields are carried so a v1 peer accepts the handshake, but the congestion loop is `bbr`, not Brutal. `bbrProfile` is the remaining unfilled key: the name is accepted and refused exactly as the reference does, but quiche's custom-BBR knobs sit behind an internal-only feature, so stock BBR2 stands rather than a silently different profile.
- **A per-chunk relay clone.** The relay direction held its `Flow` behind one clone for the whole direction rather than cloning the backlog `Vec` per 16 KiB chunk.
- **The relay legs' zero fill.** Both `relay` buffers were per-flow `vec![0u8; 16384]` callocs; they now read into the same uninitialised `RelayBuf` the proxy's raw loops use. Each leg still reads the whole 16 KiB and forwards `&buf.as_mut()[..n]`, so read granularity, per-chunk copies and syscalls are unchanged — what retires is the two memsets per flow, witnessed by the CI RSS matrix, not by a count row.
- **The per-flow handshake.** Every dial used to pay a full QUIC handshake and a `POST /auth` for one stream. The dialer now pools one authenticated connection per outbound — keyed on host, address, port, congestion, auth and roots — and hands each flow the next stream id off it, the pinned client's own shape. `tcp-flows-per-handshake` is 2, not 1: the `HANDSHAKES` counter shows one handshake carrying two echoes (`hysteria_shares_one_connection_between_two_flows`), and a closed pooled connection pays a fresh one (`hysteria_redials_when_a_pooled_connection_closes`, `closed-connections-reused` 0).
- **A flow handed a connection that had stopped carrying data.** The pool asked only `is_closed()`, so a connection quiche had already stopped taking application data on — draining, or closed locally and not yet drained — was handed the next flow's stream; its `[0, 0]` reply had nothing to arrive on, and the dial sat out `HANDSHAKE_TIMEOUT` before redialling. `candidates` and `open_pooled` now ask `usable` — not closed, not draining, no local or peer error — so the redial gate reaches its fresh-handshake assertion without the wait. A connection that drains between the hand-out and the reply is caught on the flow's first read, under the reply's own `HANDSHAKE_TIMEOUT`: `usable` is asked at the hand-out and at the eviction, and `open_flow` no longer blocks for the reply.
- **The opening reply's blocking wait.** `open_flow` read `[0, 0]` before returning, so an upload-only flow against a server that buffers the acknowledgement until its first downlink byte — xray-core's VLESS inbound does — deadlocked until `HANDSHAKE_TIMEOUT`. The reply is now owed to the flow's first read (`Flow::reply`, `drain_reply`), so the opening write returns at once and an upload-only flow never waits for a downlink that will not come; the read's wait is bounded by `HANDSHAKE_TIMEOUT`, so a reply that never arrives ends the flow instead of parking it forever. `hysteria_client_passes_a_hand_rolled_server` withholds `[0, 0]` until the server has read one upload byte; the test completes in 0.10 s, where the old shape waited out the budget. A refused flow is closed on its stream (`io.close()`), so the first read sees FIN rather than a reply that will not come; `hysteria_server_ends_a_flow_it_refuses` ends in 0.12 s.
- **A read that left the window update queued.** `Flow::read` consumed stream bytes but never flushed the connection, so the peer's `MAX_STREAM_DATA` waited for the router's next packet or its 100 ms idle tick; an upload-only server leg capped at one window per tick. Every read now flushes the egress it unblocked, so the server releases the next window as it drains. This is a throughput fix, not a byte change; the loopback suites read the same stream. The cost is one `conn.send` sweep on a read that consumed stream data; a read served from the backlog pays none.
- **Eight zeroing passes on the flow paths.** `drive_once`'s receive room (1350 bytes), `serve_loop`'s packet buffer and the router's output buffer (1350 each), `serve_stream`'s head room (64), `drain_settings`' room (128), and the 4096-byte rooms in `read_headers_block`, `auth_exchange` and `read_request` all opened zeroed and were overwritten in full by the first read. Witnessed in machine code like the quic carrier's own removal: the aarch64 dev-profile asm of `ferrox-app` goes from 9 `_bzero`/`_memset` calls across `ferrox_app::hysteria` frames to 0 — whole-file zeroing calls 91 → 82 — and the bytes did not move, because the loopback, hand-rolled client/server and pinned-client suites read the same stream.
- **The request path's copies.** `serve_stream` used to slice the prefix off (`head[prefix..].to_vec()`); `read_request` used to rebuild the backlog with `flow.backlog[flow.at..].to_vec()` and then still drained the `0x401` prefix before parsing, moving every byte behind it to the front; `read_headers_block` used to `to_vec` the header block; `auth_exchange` used to `to_vec` the auth body before verifying it. The prefix now stays in the buffer with a cursor stepped over it, and each parse reads what already arrived: `a_parsed_request_leaves_its_payload_where_it_landed` pins the backlog's base pointer, capacity, prefix bytes and the payload's own base across the parse (`request-parse-reallocations` 0, `request-parse-moves` 0), and the other three sit under the same loopback and pinned-client gates that read the auth bytes.
- **The outbound fragment list.** `fragment_udp` built a `Vec<UdpMessage>` for every reply and every client uplink datagram, even when the peer's window carried the whole payload in one fragment. `fragments_udp` is an iterator over the message's own payload chunks, so the common one-fragment datagram and the split one both walk their fragments without a heap list; `a_fragment_run_takes_no_heap` holds a 1200-byte window over 4096 runs at 0 allocations, 0 bytes and 0 zeroed (`udp-fragment-list-allocations-per-datagram` 0). What the lane still pays, named: one `encode_udp` validation per fragment, the caller's reused wire buffer, and the `dgram_send` itself.
- **The route walk at every Initial.** `route_packet` scanned every route and compared both its initial DCID and its client CID to find the lane a retransmit belonged to, so a retransmit cost one walk per route in the table. `Router` now carries `by_client_cid` and `by_initial_dcid` reverse maps, filled on `accept` and dropped with the route in `idle`, and `initial_route` is a hash probe on the initial DCID, then on the source CID, with one route-table check. `a_retransmitted_initial_reuses_its_lane_without_a_second_route` drives a real client Initial through `route_packet` and then the same packet again, pinning one route and one reverse name each, a source CID alone naming its lane, and the existing connection's receive counter advancing when the client's next flight is driven on it; `an_idle_reap_drops_a_closed_routes_reverse_names` pins that reaping a closed route clears both maps. The bytes a valid retransmit is driven on do not move, because both CIDs name the same route there. What is not removed: each route now holds a cloned client CID, a cloned initial DCID and a cloned route key in the two maps; and a packet whose DCID and source CID name two different routes — not a valid QUIC state — now prefers the DCID, where the old pick was the map's iteration order.
- **`Router::idle`'s two passes and the per-packet SETTINGS drain.** `idle` collected dead route keys into a `Vec` and locked every surviving route twice; it is one `retain` pass with one lock per route. And the server used to pay `stream_recv` on stream 2 for every packet; a `settings_done` latch set on the stream's FIN retires the call, found with the same one route lookup that feeds the auth state. The datagram reap enters through the same `retain`, touching each flow once.
- **One turn, one egress sweep, one lock.** `drive_once` took exactly one datagram per turn, so the pump and the v1 readers paid a lock, a `flush_egress` sweep and a latch bump per packet, and a reader fed back-to-back packets woke and swept for each one. A turn now takes the queue already behind the datagram it waited for — one `recvmmsg` batch of `RECV_SLOTS` (8) where the lane's read is the wire's own, and the same count of single reads behind a 1 ms tail where a mask or a relay frame rewrites each datagram — so one turn covers up to nine packets with one lock and one flush. `a_turn_takes_the_datagrams_queued_behind_its_first` pins the granularity: eight queued, one turn, none left unread (`datagrams-per-turn-witnessed` 8), and the same test reads seven left on the per-packet shape. The `recv_from`/`send` delta belongs in the syscall table `scripts/count-ops.sh` prints, not in a loopback assertion, because a loopback count is the scheduler's. What the turn still pays, named: one `conn.recv` and its quiche packet processing per datagram — the bytes are still parsed one at a time — the 1 ms tail arm when the queue runs dry, and on an obfuscated lane the unmask and its scratch copy per datagram.
- **The narrow rooms on masked reads.** `pump` and the v1 `serve_loop` read a masked lane through a `MAX_DATAGRAM` buffer, so `masked_read` fell back to a salt-wide scratch and copied every plaintext datagram back; both rooms are `RECV_ROOM` now, and `an_obfuscated_read_unmasks_where_the_wire_bytes_landed` is the pointer/tail witness. What it does not remove: a masked lane is still one `recv_from` per datagram, because its bytes are not the wire's own.
- **The server's receive turn.** `serve_loop` took one datagram per `recv_from`, so a client's burst paid a syscall and a route parse per packet. On Linux the turn is one `recv_batch` of `RECV_SLOTS` (8), each datagram routed from the batch's own slot; an obfuscated lane is not batchable, so it keeps the per-datagram `recv_from` and waits on the socket's own `ROUTE_POLL` (100 ms). The bytes are unchanged, and the `recv_from` delta is the CI matrix's server leg rather than a loopback count.
- **Two threads, one socket, each remembering its own wait.** `drive_once` is shared by the TCP pump and the UDP reader of one association, and both hold the same `Arc<Datagram>` — and `SO_RCVTIMEO` sits on the file description, not on the handle, so the two arm one clock. The reader's budget is `UDP_POLL` (1 s), the pump's is `STREAM_POLL` (5 ms), and each used to keep its own note of what it had armed: whichever armed last won the socket, and the other skipped its arm on every turn after, so a pump whose note said "5 ms applied" slept out the reader's second per datagram — two hundred times the poll it asked for — or a reader spun at the pump's rate. The note is one cell inside `quic::Datagram`, shared by every handle of the socket and read before any skip, so a holder can only skip an arm the description really carries; `drive_once` lost its `applied` parameter and its four callers lost the locals with it. `a_wait_undone_by_another_handle_is_armed_again_before_the_read` is the witness, and it is the quic carrier's rather than one written per carrier, because the bug is in the socket seam both ride: it asks 400 ms through the first handle after a second has armed 4 ms, and returns at 4.5 ms on the per-handle shape. No count moves here and none is claimed — this is a wait that was being missed, not a syscall that was being saved; the re-arms the fix makes necessary are named on the quic page.
- **The cover page's type, decided from one word.** A static file's `content-type` was the extension lowered into a fresh `String` and matched against twenty names; it is now the extension padded with spaces to eight bytes, one `| 0x20` and one length, so the whole decision is a register compare and the request path allocates nothing (`masquerade-file-type-allocations` 0). The fold is exact rather than approximate: a byte that ORs into a lower-case letter is that letter in either case, and no other byte ORs into one, so an unknown extension cannot be folded into a known one — which is what `every_extension_answers_as_the_lowercase_match_did` sweeps, every name in every case beside the length and non-ASCII traps. The same shape retired the chunked test's own `String`: `transfer-encoding` is now read seven bytes at a time in either case, with `the_chunked_check_reads_every_spelling_the_lowercase_one_read` proving the two read the same spellings. The de-framed body got the same treatment: the framing is longer than the data it wraps, so the framed input bounds the answer and `dechunk` opens one buffer of its size — one allocation of exactly the input's length, capacity held at it, the doubling series gone (`masquerade-chunked-dechunk-allocations` 1), with `a_chunked_body_deframes_into_one_buffer` holding the capacity and comparing every chunk width and every malformed shape against the doubling loop kept as the oracle. What was **not** removed, named: the origin response's headers still become a `String` each in `Vec<(String, String)>`, because that type is what the caller re-emits; `dechunk` still parses a hex length per chunk; and the cover answer still copies the file's bytes into the frame it emits.
- **A decode of a path with nothing to decode.** `safe_path` percent-decoded every static request into a `Vec` and then re-validated the decoded bytes as UTF-8 — two passes and a buffer for a request line that almost never escapes anything, where the decode of a percent-free path is the identity. `percent_decode` now asks for a `%` first and lends the request's own text back when there is none, opening its one buffer only for a path that escapes a byte, so the common static request pays no decode at all (`masquerade-path-decode-allocations` 0, and one for `/a%20b`), and `every_path_decodes_to_the_bytes_the_buffer_form_decoded` sweeps the escapes, the multi-byte ones, `%25` and the half-escapes that reject the whole path against the buffer form kept as the oracle. The whole answer over a real file is `a_static_file_answer_opens_only_the_path_and_the_file` — the path it builds and the one growth that path takes over the platform's own `is_dir` and `fs::read`, priced against that platform work measured in the same process so a standard library that opens more for a file is a floor and not a budget, 2 buffers (`masquerade-static-answer-allocations` 2) — where the type's `String`, the decode's buffer and the answer's block used to be three more. What was **not** removed, named: the path is still a `PathBuf` built segment by segment, and it is still checked with `is_dir` and opened by `fs::read` on every request.
- **The served router's own egress loop.** `Router::{accept, drive, wake, idle}` and `auth_exchange` answered through a private `flush` that wrote one `send_to` per datagram quiche handed out, so a turn that produced a burst cost a syscall per packet on the server side — the one place that did not ride the batched sweep the dial already had. The router now calls `quic::flush_egress`: one `sendmmsg`, or one `UDP_SEGMENT` message for a full run to one peer, per burst, with the per-packet `send_or_hold` kept only where the socket cannot batch (a mask, a hop, a relay frame). The bytes did not move — every datagram is the same buffer to the same peer in the same order — and `hysteria_carries_vless_echo_over_loopback`, `hysteria_carries_udp_echo_over_loopback`, `hysteria_server_passes_a_hand_rolled_client` and the pinned-client suites read the same streams. What went with it: the `Router`'s 1350-byte output room and the `out` slice threaded through ten call sites, and a refused write that used to be dropped — a QUIC DATAGRAM frame is never retransmitted, so the loss was an inner hole only a retransmit timer repairs — is held and retried by the next sweep, because that is what the shared egress already does. The `sendto`/`sendmmsg` split in the syscall table under `hysteria::serve_loop` is where the change is read; a loopback count is the scheduler's, so it is not an assertion.

What is **not** removed, and is named rather than claimed: the pool is one process-wide map per outbound key with no eviction policy beyond pruning closed, stale and stream-exhausted entries on the next dial, so an outbound burst holds one connection each for `REUSE_WINDOW` (150 s, half the idle timeout); the client's UDP lane rotates associations on one connection rather than retiring the connection per destination, so a retired flow's late datagrams land on the floor by the never-reuse rule; the masquerade site's `proxy` cover dials `http`, `unix` and `https` origins — the second on either host family, since the unix scheme is served by the transport seam rather than a `#[cfg(unix)]` side of its own, and the last through the same client TLS the relayed lane already speaks, verified against the platform roots or trusted as presented when the config names `masq_url_insecure` — and every origin request pays a fresh connection closed after its buffered response, so a hot cover page re-dials instead of pooling; 0-RTT, migration and key updates are quiche's; the server keeps one UDP socket per inbound with a per-connection route map and the two reverse maps an Initial is routed through.
